The ASE Waveform Viewer

A user guide for the waveform window of ASE-L, xschem's analog simulation environment. Written for someone opening it for the first time. The simulation cockpit itself — analyses, outputs, running — is covered by the ASE-L tutorial.

This guide is about the ASE Waveform Viewer: a window of its own that plots a .raw file. It is not about graphs embedded in a schematic drawing, which are a different surface with their own manual page — see Graphs in schematics. The two share the same drawing engine, so many gestures feel the same, but the window around them is not the same window and the keys are not the same keys.

1. What the viewer is

The viewer is a real xschem editor window that has been repurposed as a plotting window:

  • it is read-only for its whole life — nothing you do in it can dirty a file, and no save prompt can ever appear;
  • the editor toolbar and the editor menus are gone and replaced by a small menubar of its own: File, View, Graph, Cursors, Options;
  • every editor key and mouse gesture has been stripped off its canvas, so the keys listed in §9 are the whole vocabulary of the window. Anything not listed there does nothing at all, silently;
  • the plot fills the window. Nothing in the viewer scrolls or zooms the canvas — every zoom and pan changes the data range of a plot.

The title bar reads Waveforms <cell> (<state view>). Each ASE session owns at most one viewer: asking for it again raises the window you already have.

It writes no .save cards of its own, though — a descended internal node is only plottable if the run actually saved it (an explicit output, or the save-all-voltages option).

2. Strips, traces and the target strip

The window is a vertical stack of strips. A strip is one plot box with its own axes; the strips are laid out as equal horizontal bands filling the window, so adding a strip makes them all shorter. A strip holds any number of traces. Trace names are listed along the top of each strip — that band is the legend, and it is clickable (§7).

One strip is the target strip: the one new signals land in. When more than one strip is up, the target is marked by a dull-yellow bar at its right-hand edge. Clicking anywhere in a strip makes it the target.

Single-plot and multi-plot mode

Where a Direct Plot batch lands is decided by the window's plot mode:

ModeA Direct Plot of three signals gives you
single (the default)all three traces in the target strip.
multithree strips, one signal each, stacked newest on top.

Switch modes with Options > Plot Mode (one entry, which always offers the other mode), or with Ctrl-Shift-4 on the schematic window. The bottom status bar shows the current mode (Plot: single). An empty strip left behind by Clear All or Add Graph is reused before a new one is appended, in both modes. The auto-plot strip is never used as a landing site.

The initial mode of a newly opened viewer comes from the config variable wviewer_plot_mode; once a window is open, that window's own mode is what counts.

3. Getting traces in

From the Outputs table

Tick Plot on an Outputs row in the ASE window. After the next successful run that expression is plotted into the auto-plot strip. Untick it and it disappears from that strip after the following run. Nothing else in the window is touched.

Direct Plot

Enter the mode, click the nets and devices you want, press ESC. Each clicked net is painted on the schematic in the colour its trace is about to get, so you can tell which curve is which before the plot exists. Direct Plot does not add anything to the session Outputs, and its strips are never rebuilt by a later auto-plot.

Graph > Add Trace…

The Add Trace dialog has a Graph: combobox (shown only when there are at least two strips; it defaults to the last one), an Expression: entry, an optional Name (optional): entry, and a listbox headed Raw variables (double-click to use):. Double-clicking a variable copies it into the expression entry; pressing OK with an empty entry uses the listbox selection. Return in either entry is OK.

A single token is a raw-vector reference. It is matched case-insensitively and v(...) wrapping is applied where needed, so out finds v(out).

Several whitespace-separated tokens are an RPN expression, and it is validated before it is accepted — a bad token keeps the dialog open with a message such as unknown token '<t>' (not an operator/function, number or raw variable). Operators:

+ - * / ** == != > < >= <= ?

Functions:

atan() cph() asin() acos() tan() sin() cos() abs() sgn() sqrt() tanh()
cosh() sinh() atanh() acosh() asinh() exp() ln() log10() integ() avg()
ravg() max() min() im() re() pi() k() e() q() del() db20() deriv()
deriv0() deriv2() deriv20() prev() exch() dup() idx()

Numbers may carry SPICE suffixes (1k is fine). An RPN expression is materialised as a new raw vector named after your Name (or expr<N>) and then plots like any other variable.

The re-run caveat. Each run overwrites the session's .raw file and the viewer re-attaches it. Ordinary traces simply show fresh data. An RPN expression trace loses its computed vector on the re-attach and draws empty after the next run — the vector it referred to no longer exists. Re-add the trace, or save the state and load it again (the reload re-materialises every expression trace).

4. Reading values off the plot

The snap diamond and the status bar

Move the pointer across a strip and a small diamond follows it, sitting on the nearest real sample of the nearest trace. The bottom status bar shows that sample's x and y in engineering notation. The diamond is what tells you where a marker would be created — it and the m key ask the engine the same question. It disappears while any drag is in progress.

Cursors A and B

Turn a vertical cursor on from Cursors (checkbuttons Cursor A, Cursor B) or with a / b over a strip. From the menu the cursor is parked at the middle of strip 0's x range; from the key it lands at the pointer. Cursors are shared by every strip, which is what makes them useful on a stack of time-aligned plots.

  • Drag a cursor by pressing near its line and moving the mouse. The grab band is generous — a few tens of pixels — and a press that lands in it belongs to the cursor, whatever else is underneath.
  • Set one numerically: right-click in that same band and a Pos: input appears.
  • s swaps A and B (both must be on).
  • A and B (shifted) put horizontal cursors on the strip under the pointer, at the pointer's y. Those are per-strip, not shared, and they drag and set numerically the same way.

The readout bar

Cursors > Readout shows a bar at the bottom of the window with one line per enabled cursor: the cursor's x, then the interpolated y of every trace in the window, engineering-formatted —

A: x=905m   v(g)=905m   v(d)=1.02   i(v1)=-409.7u

It refreshes on every mouse-button release. Enabling a cursor from the menu turns the bar on automatically. Cursor state is not saved with the session.

The measurement tooltip

M (Shift+m) over a strip toggles a small floating readout that follows the pointer and shows the x and y of the pointer — not of a sample. Press M again to turn it off; it also stops when the pointer leaves the strip.

Markers

A marker is a permanent annotation pinned to one sample of one trace: a dot on the trace, a leader line, and a callout box reading

M3:1.2u,905m

Press m anywhere inside a strip's plot box and a marker is created at the sample the diamond is showing. Press d instead and the new marker also carries a delta block against the previously created marker:

M4:2.4u,1.51
Δx:1.2u,Δy:605m
slope:504.2k

Both markers keep their own identity, and the pair is a unit for selection: double-clicking either one selects both, even when they sit on different strips. Deleting a marker that another one measures against silently degrades that partner to a plain callout.

  • Drag the dot and the marker slides along its own trace, snapping from sample to sample; the readout follows as you drag.
  • Drag the callout of an unselected marker and only the box moves.
  • Drag the callout of a selected marker and the whole marker translates — the dot re-snaps along the trace and the box keeps its offset.
  • ESC mid-drag cancels; nothing is committed.
  • Delete over the strip deletes the selected marker (see §6).
  • Ctrl-E deletes every marker in the window, leaving the strips, traces and ranges alone.

Markers are saved with the session state; cursors are not.

What is shared and what is per-strip

The X axis is the axis the strips have in common, so every X change hits every strip: an X zoom, an X pan, a box zoom's X half. Y is the opposite — each strip carries its own signal scale, so Y changes only the strip under the pointer. That rule holds for the wheel, the keys, the menu and the box zoom alike, and it is why the stack never slides out of step with itself.

Graph > Shared X Axis goes one step further and forces every strip to show strip 0's x window. Turning it off gives every strip its own window back — the per-strip settings are kept while sharing is on, not overwritten.

The Axes dialog

Graph > Axes… opens a dialog with a Graph: combobox and four entries — X min (blank=auto):, X max (blank=auto):, Y min (blank=auto):, Y max (blank=auto): — plus Log X and Log Y checkbuttons. Changing the combobox loads that strip's current values. A blank field means auto-range: that axis is re-fitted to the data every time the window is rebuilt.

Clear All is not "close and reopen"

Clear All drops every strip and every trace and leaves one empty strip. It deliberately keeps the plot mode, Shared X, the cursors and — the point of the whole thing — the loaded raw data, so you can immediately pick new signals from the same results without re-running the simulation.

Undo and redo

u undoes the last structural edit and U (Shift+u) redoes it: strip reorders, trace moves, splits, deletes and marker changes, up to 50 deep per window. A pan, zoom or selection made with the mouse in between comes back with the undone edit rather than being thrown away.

Window options are outside the history on purpose — the plot mode, Shared X, the grid, the cursors and the loaded raw are not undoable, and Ctrl-G is not an undo step. The history is per window and is never saved: it is cleared when the window opens and when a state is loaded.

7. Selecting traces

A selected trace is drawn bold, on the plot and in the legend. The selection is a set and it is window-wide, not per strip.

  • Click a trace (within about 10 pixels of the curve) and the selection becomes that trace — including clearing a selection on another strip.
  • Click its name in the legend for the same effect. On a digital or bus strip this is the only way, because their bodies are drawn as bands rather than curves and answer "no trace here" everywhere.
  • Ctrl+click adds an unselected trace to the set or removes a selected one, and touches nothing else — this is how a selection spanning two strips is built.
  • Click empty plot space and the selection is cleared. A click that lands in an axis margin or on the reorder grip changes nothing.
  • A plain click never deselects the trace it lands on; clicking the already-selected one keeps it.

What a selection is for: Delete deletes it, a drag carries all of it to another strip, 9 highlights it in a style of its own (§9.1), and the bold is a way of keeping track of one curve in a crowded strip.

Markers have their own, separate selection — one marker, or a delta pair. It is set by clicking a marker and cleared by clicking empty space.

8. Saving and reloading

The viewer layout is part of the ASE simulation state, not a file of its own. Save State in the ASE window stores, per session: whether the viewer was open, the strips and their traces (expressions, names, colours, axis ranges, log flags and markers), the Shared-X flag, the plot mode and the target strip.

Loading a state whose viewer was open brings the window back, re-attaches the raw file if it is still on disk, and re-materialises the RPN expression traces — which is why a save/load cycle is a working repair for the empty expression traces described in §3.

Not saved: the cursors, the grid on/off state, the undo history, and the raw samples themselves (only the path to the .raw file is kept).

What a trace highlight is, and what it is not. It is window chrome: it is never saved, never exported (a printed or SVG plot carries the trace, not the highlight), and it dies with the window. Highlighting a trace does not highlight the matching net in the schematic, and vice versa. A blinking or marching style is drawn from a cached per-pixel envelope of the curve rather than from the samples, so it costs the same on a 200-sample trace and on a 200 000-sample one — with three visible consequences, all deliberate: a repainting highlight briefly rubs out the snap diamond where they overlap (it comes back on the next mouse move), the marching phase follows the drawn band rather than the exact curve length, and the dashes scroll in whole pixels, just as a marching wire highlight already does. Digital and bus traces are drawn as bands, not curves, so 9 refuses them and highlights the analog members of the selection instead.

9.5 The same key in a schematic window

Six of the viewer's keys are also shortcuts in a schematic, and they mean different things. They do not collide — a viewer canvas does not carry the schematic bindings — but knowing both meanings saves a surprise:

KeyIn a schematic windowIn the viewer
Ctrl-EGo back one level of hierarchy Delete all markers
eDescend into the selected instance Delete empty strips
Ctrl-GToggle the global dot grid of the drawing Toggle this window's graph grid
9Highlight the selected net, or click nets to highlight them (with cadence_style_rc) Highlight the selected trace(s)
8Un-highlight the selected net, or click nets to un-highlight them (with cadence_style_rc) Un-highlight the selected trace(s)
0Un-highlight every net (with cadence_style_rc); toggle a pin's logic level otherwise Un-highlight every trace

The last three do the same job on the other kind of line, out of the same style table — the one net_hilight_style table an rc defines, so a style you wrote for wires is available to traces unchanged. Three differences are worth knowing:

  • In a schematic those keys exist only if you load src/cadence_style_rc; in the viewer they are shipped defaults.
  • A schematic 9 with nothing selected starts a click-to-pick mode. The viewer's refuses instead — it already has a first-class trace selection, so there is nothing to pick.
  • The style cursor is per window, so the viewer keeps its own place in the table and pressing 9 there does not move the schematic's. There is no Alt+- in the viewer either (that is a bind .drw in the rc, and viewer canvases do not carry .drw's bindings) — to reach a particular style from the viewer, name it: bind a key to wviewer::apply_style_traces_at %W {…} (§10.1).

The viewer has no dot grid at all — it is suppressed for the window's whole life — so Ctrl-G there can only mean the graph grid.

10. Changing the keys and the defaults

Everything in this section goes in an rc file: ~/.xschem/xschemrc, a ./.xschemrc beside your design, or any file passed with --script (src/cadence_style_rc is the shipped example, and it carries commented-out versions of all of these).

10.1 The WaveViewer binding tag

The nine viewer keys of §9.1 are bound on a Tk binding tag called WaveViewer. The defaults are installed once, at the first viewer open, and only for a sequence nothing has bound yet — so an rc that binds first wins, even though it runs long before any viewer window exists.

bind WaveViewer <Control-Key-d> {break}                  ;# drop the default
bind WaveViewer <Control-Key-r> {wviewer::clear_all_at %W; break}

The commands each key calls, all taking the event's own widget (%W) so the right window is edited even if the pointer and the keyboard focus disagree:

DefaultCommand
Ctrl-Dwviewer::clear_all_at %W
Ctrl-Ewviewer::delete_all_markers_at %W
ewviewer::delete_empty_strips_at %W
Ctrl-Gwviewer::grid_toggle_at %W
uwviewer::undo_at %W
Uwviewer::redo_at %W
9wviewer::hilight_traces_at %W
8wviewer::unhilight_traces_at %W
0wviewer::unhilight_all_at %W

One command has no default key of its own: an ad-hoc highlight style, written out in the binding instead of picked off the style table. It takes the same three argument forms apply_hilight takes for nets — named fields in any order, a Tcl dict, or a positional style row — and any field you leave out takes its default:

bind WaveViewer <Key-F5> \
  {wviewer::apply_style_traces_at %W {color purple thickness 3 pattern {20 20}}; break}

That needs utils/apply_hilight.tcl sourced, which src/cadence_style_rc does. The style is installed into the table once (an identical row is reused, so a key you press fifty times does not grow it fifty rows) and applied by its index like any other.

Disable with {break}, never with {}. An empty script deletes the binding, and a deleted binding reads as "nothing has bound this yet" — so the default is installed over it at the next viewer open and the key comes back. {break} leaves a real, do-nothing binding in place.

Why a tag and not the canvas widget. The viewer sweeps every binding off its own canvas when the window is built — that is how the editor's keys and any bind .drw lines from your rc are kept out of a read-only plot window. A bind $canvas of your own would be swept with them. The tag is not swept, and it exists before any viewer window does.

The menu entries in §9.1 keep working whatever you rebind: their accelerator text is a static label, not a dispatch, so after a remap the label is the one thing that goes stale. Change it in your rc too if it bothers you, or use the menu.

10.3 The action registry and the bindings files

xschem has a general remapping mechanism — xschem bind key <keysym> <mods> <context> <action>, and the keybindings.csv / mousebindings.csv files that are replayed through it at startup. Stated plainly, because guessing wrong here costs an evening:

  • It does not reach the viewer's own keys. A row in the canvas context is dispatched by the C engine, and the viewer never hands the engine anything except the nine graph keys of §9.3. Rebinding canvas changes the schematic, not this window.
  • It does reach the graph keys. A row in the graph context does take effect over a viewer strip, because those keys really are forwarded to the engine. For example xschem bind key 116 0 graph <action> would change what t does over a strip, in the viewer and in an embedded schematic graph alike.
  • It never reaches a wheel gesture over a plot. A wheel event whose pointer is inside a plot is claimed by the graph engine before the binding table is consulted, so mousebindings.csv wheel rows cannot change any of the wheel behaviour in §9.4.
  • The window keys of §9.2 are not remappable today. They are handled inside the viewer before anything else sees them. A bind WaveViewer on one of those sequences runs, but it runs in addition to the built-in behaviour, not instead of it — so you can add an effect, not replace one.

10.4 What cannot be rebound

  • The mouse-button roles inside the engine — left = pick and drag, middle = pan, right = box zoom and menu — are compiled in. There is no configuration for them, and no error either: there is simply nowhere to say otherwise.
  • The pick and click tolerances (10 pixels to a trace, 8 to a marker, 3 pixels of travel before a click becomes a drag, the 14-pixel reorder grip) are compile-time constants shared by the drawing and the hit-testing, so that what is drawn and what is clickable cannot drift apart.
  • The viewer's read-only-ness. The window cannot be made editable; that is what guarantees no plotting session can ever modify a schematic.

11. Troubleshooting

SymptomWhy, and what to do
Nothing plotted after a run, and no viewer opened No Outputs row has Plot ticked. Auto-plot has nothing to do and deliberately does not open a window. Tick a Plot box and re-run, or use Direct Plot.
ase: op results have no sweep — nothing to auto-plot The run produced only an operating point. There is no x axis to plot against. Enable a dc, ac or tran analysis; op values are read in the Outputs table's Value column instead.
The traces went empty after a re-run Those are RPN expression traces. Their computed vector does not survive the re-attach of the new .raw. Re-add the trace, or save the state and load it back — the reload re-materialises them (§3).
A Direct Plot pick produced no trace The node was not in the raw file. Direct Plot writes no .save cards, so an internal node is only plottable if the run saved it. Add it as an output, or turn on save-all-voltages, and re-run.
The viewer will not open The viewer belongs to an ASE session: open the cell's ngspice_state view first. Without a session there is nothing for the window to belong to and you get ase: cannot open the waveform viewer for <session>.
A key "does nothing" Most likely it is one of the §9.3 keys and the pointer is not over a strip — those are gated on pointer position, not on keyboard focus. Move the pointer onto a plot and try again.
A drag reorders the stack when you meant to move a trace The press must land within about 10 pixels of the curve. Further out is "empty plot space", which is the strip-reorder grab. Watch the pointer: it turns into a grab hand for a trace drag and into a vertical double-arrow for a strip drag.
Clicking a trace on a digital or bus strip selects nothing Those are drawn as bands, not curves, so there is no curve to be near. Click the name in the legend instead — that always works.
A zoom or pan came back after resizing the window Resizing rebuilds the strips from the stored layout. Ranges you set through Graph > Axes…, the wheel or the keys are stored; some engine-side gestures are view state that a rebuild discards. Use Axes… when a range has to stick.
The window title reverted to untitled.sch Cosmetic. Move the pointer over the viewer and the title is restored.
