## 3. What changed, item by item

1. **`_origin()`** — `env -u GIT_DIR -u GIT_WORK_TREE -u GIT_COMMON_DIR git -C
   "$HERE" rev-parse --path-format=absolute --git-common-dir`, with a trailing
   `/.git` stripped; fallback `cd "$HERE/../.." && pwd -P`. `repo_via:` records
   `git`, `path`, or `told`. Computed **once at load** (a lazy version inside
   `$( )` cannot memoise back into the parent and would fork git once per
   entry). The `env -u` and the `/.git` strip are additions to PLAN — see §5.
2. **`cmd_add` stamps** `repo:` + `repo_via:` on lines 2+. Line 1 still has
   exactly three tab fields (checked: `awk -F'\t' '{print NF}'` → 3).
3. **Cross-origin `add` refuses**, exit **5**, writes nothing.
4. **Cross-origin `clear` refuses**, exit **5**, prints the owning clone, the
   entry's reason, and this clone's own ids on that number — or says plainly it
   owns none.
5. **`--repo <clone>` on both**: a clone path, its basename, or `here`.
   `add --repo here` files `<id>@<tag>` (the **subject** is untouched, so the
   `ref:` still resolves — that is the whole reason the suffix workaround was
   rejected); `add --repo <their tag>` updates their entry and keeps their stamp
   **verbatim**; `clear --repo` prefers the `<id>@<tag>` slot.
6. **`drain` skips** a foreign suite debt, keeps it, counts it separately and
   still exits 0 (a skip is not a failure).
7. **Both rewrite arms** go through `_rewrite_line1`, which rewrites line 1 and
   `tail -n +2`'s the rest. Temp file in the state dir **root**, not the kind
   dir, because `cmd_list` globs the kind dir.
8. **Unattributed = proceeds + one warning + claimed on the way through.** One
   narrowing, added on evidence — see §4.
9. **`list`/`show` mark** a foreign entry and a ref that does not resolve here.
   Everyday single-clone output byte-identical (proved: `diff` against HEAD's
   output over the live ledger differs by exactly the one new marker).
10. **`cleared.log`**, append-only, in the state dir root: every `clear`, every
    `add` overwrite, **and** every debt a drain clears on a pass.

* **PLAN's "42 of 132 rule entries point at a file only this clone has" is

  standing in the shared ledger under the bare id, which is the collision
  itself. The corrected numbers are in the code comment and in R608.
* **PLAN's suite claim holds exactly.** Of the 8 suite debts standing, 7 resolve
  here, all 7 also resolve in op-wcard, and **6 of those 7 differ in content**
  (`cmp -s`). The 8th, `test_hier_pdf_links_1333`, resolves **only** in
  op-wcard.
* **That 8th debt forced a narrowing of item 8.** A plain "stamp every
  unattributed entry on the way through" means the next `drain` from this tree
  claims op-wcard's `test_hier_pdf_links_1333` as ours — this tree then owns a
  debt it cannot run, and op-wcard is refused on its own. So `drain` claims an
  unattributed suite debt **only when its name resolves in this clone**; a name
  that resolves nowhere here stays unattributed and is reported by R309 exactly
  as before. `add` and `clear` claim unconditionally, as PLAN says.
* **`add --repo <tag>` had to stop rewriting the stamp.** First implementation
  stamped what the user typed, so `add rule 1344 --repo cloneA` replaced clone
  A's full id with the tag `cloneA` — and clone A then read its **own** entry as
  foreign. Caught by V5. A matching update now keeps the standing stamp
  verbatim, and a bare tag with no standing entry is resolved against the
  ledger's own stamps before being written.
* **`clear --repo here` had to prefer the namespaced slot.** Also caught by V5:
  it found the bare id first and refused. `clear --repo` now prefers
  `<id>@<tag>`, so whatever `add --repo` created the matching `clear` reaches
  with the same words.
* **The plan lists only R608 and R609. I added R610** for `cleared.log`: every
  other behaviour in this file has a requirement number, and N3 needs a contract
  to write O33 against.
* **`list` got FASTER, not slower.** Three `sed` subshells per entry × 192
  entries was already the cost; my three extra field reads would have made it
  2.39 s → 2.96 s. `_read_opts` reads each entry once in the current shell
  instead: **1.36 s** measured, against **2.39 s** at HEAD.

## 5. Deviations from PLAN, and why

* `env -u GIT_DIR -u GIT_WORK_TREE -u GIT_COMMON_DIR` around the `rev-parse`:
  inside a git hook those name whatever repo invoked the hook.
* the trailing `/.git` is stripped from the git answer, so the git id and the
  path-fallback id name the **same** clone. Without it, a tree that loses git —
  or one whose git predates `--path-format` (2.31) — turns every one of its own
  entries foreign in a single step.
* exit **5** is new and is reserved for the refusal (2 usage, 3 state dir, 4 no
  such debt). PLAN says "non-zero"; N3 needs a number.
* `add` now prints **`updated`** instead of `recorded` when it replaces. PLAN's
  problem statement names that lie ("It prints `recorded`, never `replaced`")
  and nothing greps for the word.

## F4 — what I did, and why it is not a removal

The escape is **not** removed. What changed is what `show` advertises.

`show` used to print, for a foreign entry,
`clear with: …/owed.sh clear look <id> --repo cloneA`, and that command works —
the adversary ran it and cleared another clone's look debt at exit 0. The
original argument was that a queue telling the user to type a command that gets
refused is worse than one that says nothing. That is true of a **user at a
keyboard**; it is wrong here, because the failure this whole item exists to stop
is an **agent** in clone B closing a ruling the user has never answered in clone
A — and `show` was handing that agent the exact bypass, with no friction and no
statement of consequence. It removed every cost from the one operation R609
exists to make expensive.

So, per the driver's direction: `show` prints the **plain** command and names
the owning clone; the refusal — read by someone who has just been told no — is
the one place `--repo` appears. `help` still documents it. Measured:

## D3 — the choice, and why

**Chosen: warning-and-refusing on `add`; warning-and-proceeding on `clear`;
skip-without-claiming on `drain`; and a mark in `list`/`show`. Never claim on
absence.** Rejected: uniform claiming (that is the defect), and uniform
refusing.

The argument is *who types the command*.

* **`add` is the automatic path.** An agent recording new work is exactly what
  ran over the top of the evidence in the measurement below. An automatic write
  must not paper over a destroy, and the user loses nothing by a refusal: the
  slot is one flag away (`--repo here`), and the refusal names it.
* **`clear` is the one command only the user is entitled to run**, and it is
  where a refusal turns into the user locked out of their own queue — the
  failure D5 measured at full scale. It also now leaves a pre-image (R610), so a
  wrong clear is recoverable, and a wrong refusal is not merely annoying but
  destroys the thing the ledger is for. So it proceeds, loudly, and says it is
  **not** a legacy entry.
* **`drain` is a machine verdict**, and the rule this file exists to protect is
  that a machine verdict may not discharge a human one. A debt this tree was
  never given must not be cleared by a pass in this tree.
* **`list`/`show` mark it**, which the finding did not ask for and which I think
  is the most valuable half: the user reads `show` before they type `clear`, and
  until this round the queue said nothing at all about an entry that had been
  written over their ruling.

**How LEGACY and FOREIGN are told apart.** FOREIGN needs **both**: stamped
entries are the majority of the ledger, **and** the entry was written after the
**oldest** stamped entry. Everything else is LEGACY and behaves exactly as
before, wording included — which is the requirement that other, never-backfilled
checkouts keep working, and it is why `test_owed.sh`'s O32 rows (a legacy-world
fixture) still pass untouched.

⚠ **I got this wrong once, measured it, and changed it.** The first rule was
"newer than the **newest** stamped entry", which reads well and is worthless:
the very next `add` from this clone raises the newest stamp above the foreign
write, and every older anomaly silently falls back to LEGACY and gets claimed.

risk is the opposite one — that it becomes a mass-attribution weapon — and that

## Owed to the user, and I cannot file it — the driver must

The live ledger is read-only to this item, so I cannot `owed.sh add rule`. Two
decisions in this round are **user-visible and unratified**, and per CLAUDE.md
they may not live in a write-up only:

1. **D3's asymmetry** — a FOREIGN `add` is refused (exit 5) while a FOREIGN
   `clear` proceeds with a warning. The alternatives are "refuse both" (safer
   against a lost ruling, and it can lock the user out of their own queue) and
   "warn on both" (nothing automatic is ever stopped). Argued above; the user's
   call.
2. **`restamp` exists at all**, and its guard is "refuse if the `--from` path
   still holds a `tests/headless/owed.sh`" with **no `--force`**. The
   alternative is to ship no command and document the manual `sed`.

Both belong against issue **1400**, and the driver must **not** use the bare id
`1400` (N1's standing warning). `--eyes` is not needed for either.
