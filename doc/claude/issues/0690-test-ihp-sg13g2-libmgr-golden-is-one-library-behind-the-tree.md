`ihp-sg13g2/xschem_libs/sg13g2_tests_ase` — and the suite's golden lists nine. That
is **two of the three FAIL lines in this branch's T1 baseline of record** (the check
itself, plus the HARNESS line it triggers).

## 2. Which side is wrong

Unresolved, and that is the reason this is filed rather than fixed. Either
`sg13g2_tests_ase` is an intended library and the golden is stale, or it is a
by-product of ASE-L work that should not be on the library path. Bumping the golden
to ten would settle the symptom and silence the question — a crew that adds a library
directory by accident would then get a green suite.

## 3. Still open

The ruling on which side is wrong, then the one-line fix on that side. Until then, T1
carries two standing FAIL lines that every crew has to re-derive as benign.

# THE RULING AND THE FIX (2026-08-25)

## 4. Which side was wrong: the GOLDEN. Five independent confirmations

The driver brief was explicit — *"regenerate the golden ONLY after confirming the
tree's list is correct; a golden updated to match a broken tree converts a red into a
permanent lie"*. So the confirmation came first, and none of it leans on the symptom:

**(a) The registry entry is tracked, deliberate and old.**
`ihp-sg13g2/xschem_libs/library.defs:13` carries
`DEFINE sg13g2_tests_ase sg13g2_tests_ase`, added by **c69b88de** and regenerated by
**bf83fa95**. `git merge-base --is-ancestor c69b88de HEAD` → **is an ancestor**.

**(b) The library is populated, not a stray directory.**
`git ls-files ihp-sg13g2/xschem_libs/sg13g2_tests_ase | wc -l` = **140 tracked files**
across **49 cells**, each a real `schematic/` + `symbol/` (+ `ngspice_state1/`) triple.

**(c) The list has no ambient contribution.** The suite pins
`library_registry_defs_only 1` and an empty `XSCHEM_LIBRARY_PATH` at its own :53-55, so
`library_list` is **exactly** that one explicit defs file's DEFINE set — measured 10
names, one per DEFINE line, no discovered defs and no personal defs.

**(d) The precedent is already ratified in-tree.**
`tests/headless/test_sky130a_libmgr.tcl:47-52` carries `sky130_tests_ase` in its golden
with a comment naming commit **15bb25ef** ("register the migrated ASE-L testbench
library"), count bumped 11 → 12, green today at 18 checks. `_ase` is the **migrated
ASE-L testbench library**, a first-class deliverable in both PDK workareas. ihp's golden
was simply one commit behind sky130's.

**(e) The control.** `gf180mcuD/xschem_libs/library.defs` has **no** `_ase` DEFINE at
all and `test_gf180mcud_libmgr` is green at 29 checks. Three siblings; only the one whose
golden lagged its own defs file was red.

Arithmetic corroboration: 65 passed + 1 failed = 66, and
`doc/claude/specs/ihp_sg13g2_workarea.md` **already recorded "66 checks"** for this
suite while still saying "exactly the 9 intended libs" two lines above — the spec's own
halves contradicted each other, which is itself evidence of which side was stale.

## 5. What changed

`tests/headless/test_ihp_sg13g2_libmgr.tcl:66-68` — the expect list gains
`sg13g2_tests_ase`, the check name becomes "exactly the **10** intended libs", and a
comment names c69b88de, **exactly as sky130's fix does**. Plus **one additive row**
proving the tenth name is a real migrated library rather than the accidental by-product
directory section 2 above feared: it resolves inside `ihp-sg13g2/xschem_libs` and a
representative committed cell is present. An executable confirmation outranks a prose
one, and it is what answers section 2's open question.

**Deliberately NOT widened**: the shared
`foreach L {sg13g2_pr sg13g2_stdcells sg13g2_tests}` "lives inside the workarea" loop —
sky130's fix widened nothing, and the whitelist stays **exact-equality**, so a library
genuinely leaking in would still redden it at 11 names. The fix does not convert the red
into a permanent lie.

Spec `doc/claude/specs/ihp_sg13g2_workarea.md` corrected in five places (tree diagram
row, "9 libraries" → 10, "9 intended libs" → 10, "66 checks" → 67, "the three PDK libs
inside it" → four).
