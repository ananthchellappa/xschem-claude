# 0505 — the viewer's Case Mode override is not persisted, and durability was never assigned to an item

**Status:** OPEN. Branch `fluid-editing` at `e998e853`. Documentation only — nothing
fixed, nothing broken.
**Area:** `src/wave_viewer.tcl` — the `Options ▸ Case Mode` cascade item 5 built, and its
`casemodeuser($token)` in-memory record.
**Found:** 2026-08-17 by the casemode batch item-13 verifier, as an OBSERVATION rather
than a defect. Filed here by the driver because **the omission is the driver's**: item 5
deferred durability to item 13, and item 13's dispatch never carried it.
**Related:** `DECISIONS.md` **B2a** (the explicit user setting is the first-ranked source);
`doc/claude/casemode_batch/receipts/05-viewer-tcl-browser-scan.md`;
`doc/claude/specs/raw_case_mode.md` §12.

---

## What

Item 5 built B2a's explicit-override control — `Options ▸ Case Mode` in the viewer
menubar — and recorded, deliberately:

> **The override is deliberately NOT persisted** — item 13 owns durability.

Item 13's scope (PLAN §3b, and the driver's dispatch) is the **`simconf` dialog**: per-row
exe/args/casemode, a Test button, probe-driven pre-fill. That is a *simulator profile*
surface. The viewer's Case Mode override is a *viewer* setting on a loaded `Raw`. The two
are different things, and item 13 correctly did not silently absorb one into the other —
it flagged that the hand-off named no owner.

So the behaviour today is: the override survives a re-attach of the **same file** in the
**same window** (item 5 built `casemode_reapply`, path-matched), and is lost when the
window closes. Nothing writes it anywhere.

## Why this may be the right behaviour anyway

Item 5's own reasoning cuts both ways, and a fix should engage with it rather than assume
persistence is wanted:

- Under the revised read design **nothing folds on read**, so an override changes lookup
  behaviour only — it is not destructive and not expensive to re-apply.
- B2a ranks the explicit setting first among four sources precisely because the other
  three are inferences. A *persisted* explicit setting outranks a fresh detection
  forever, including after the file it describes has been regenerated by a different
  simulator — which is the same staleness class as issue `0503`.
- Item 5 also ruled the override **does not reach the Ctrl-K senders**, because the
  viewer and the schematic window are separate contexts with their own `Raw`. A persisted
  session-wide mode is what B1 puts on the **simulator profile**, not on the viewer.

## What has to be decided

1. **Should it persist at all?** If the answer is no, this issue closes by writing that
   ruling into `specs/raw_case_mode.md` §12 — the point is that nobody has decided, not
   that persistence is missing.
2. **If yes, persist where** — the viewer's own state, the ASE-L session state (item 6
   added `sim_profile` to `schema_keys`/`omit_if_empty` for exactly this kind of
   question), or the graph's `.sch` attributes.
3. **Whichever way, `0503`'s lesson applies:** a recorded case decision that outlives the
   run it described is a staleness source, and this batch has now met that shape twice.

## What is NOT claimed here

No user has reported wanting this. Item 5's two `look` debts cover whether the control
*reads* correctly, not whether it should survive a restart.
