## 3. The hard/flaky split, and why it splits that way

**Run 2's fail set is a strict subset of run 1's.** 16 names failed both, 9 failed run 1
only, **0 failed run 2 only**. That asymmetry is not a coincidence and it is not a coin
flip between two equal measurements — it has a single measurable cause:

```
$ grep -c 'X connection to :0 broken'  baseline_2026-08-04_run1.log   ->  3
$ grep -c 'X connection to :0 broken'  baseline_2026-08-04_run2.log   ->  0
```

(Scribe re-ran this grep against both logs; both counts confirmed.)

The X server died **three times** during run 1. That is the documented WSLg Xwayland
abort (memory: `wslg-xwayland-aborts`) — an environment failure, not a code regression.

**Corroboration that the extra 9 fails and the extra 7 skips are the same event:**

- Every one of run 1's 8 SKIPs **PASSED in run 2**. They self-skipped on "no X" because
  the server was down at that moment.
- Three of the 9 run-1-only fails have no failing *check* at all — they were simply
  killed:
  - `test_ase_persist`: last output line is `ok: G10 redraw rc 0`, immediately followed
    by `X connection to :0 broken`. It was passing when it died.
  - `test_descend_readonly`: output is two lines — `Using run time directory ...` /
    `Sourcing .../xschemrc init file` — then `X connection to :0 broken`. **Zero checks
    ran.**
  - `test_graph_box_zoom_xy`: `TIMEOUT`, `timeout: the monitored command dumped core`.
- The remaining six fail on checks that all read *"the Tk event loop was not turning"* or
  *"the synthetic key/window event never arrived"* — see §5.

**Therefore: run 2 is the clean measurement, and the 16 names that failed both runs are
the new baseline.** A name that failed only under a dying X server is evidence about the
X server, not about the tree.

## 8. Where the logs contradicted the measurer's claim

The structured result was checked line by line against the logs. Two claims did not
survive, and one number was incomplete. **In all three, the logs win**, and the `PLAN.md`
block carries the corrected version.

### 8.1 `test_ciw`'s fail count is itself unstable — 2 in run 1, 1 in run 2

The measurer reported `test_ciw = 'no result/error text in file'` (one check). That is
right for **run 2**. But **run 1** failed **two** checks:

```
FAIL: no result/error text in file
FAIL: ciw_create re-shows
```

So only `no result/error text in file` is the stable, both-runs anchor; `ciw_create
re-shows` flaps. A verifier that sees `test_ciw` fail on 2 checks has not necessarily
found a regression — but it has not seen the baseline shape either. Recorded in the
`PLAN.md` anchor table.

### 8.2 The PDK libmgr cause is NOT the untracked scratch dirs — REFUTED

**Claim:** *"SANDBOX and TEST are the untracked scratch libraries sitting in the tree
(`xschem_libraries_oa/SANDBOX/test_sym`, `xschem_libs_newsym/SANDBOX/demo_sym_pin`, etc.
— visible in `git status`) … These three will keep failing … until those dirs are removed
or the tests learn to ignore them."*

**Refuted on three counts**, each checked directly:

1. **`SANDBOX` is registered by a TRACKED, UNMODIFIED file.** Both
   `xschem_libs_newsym/library.defs` and `xschem_libraries_oa/library.defs` carry
   `DEFINE SANDBOX SANDBOX` at line 14, both report clean in `git status`, and
   `git ls-files` shows `xschem_libraries_oa/SANDBOX/cs_amp.sch` and friends are
   **committed**. The untracked `??` dirs are extra *cells inside an already-registered
   library*, not the registration. Deleting them would not change `library_list`.
2. **`TEST` is not in any in-repo `library.defs` at all.** Both extras actually come from
   the **user-level registry outside the repo**:
   ```
   /home/qflow/.xschem/library.defs:1:DEFINE SANDBOX SANDBOX
   /home/qflow/.xschem/library.defs:2:DEFINE TEST TEST
   ```
   That is the thing to fix (or to teach the tests to ignore) — not the working tree.
3. **`test_ihp_sg13g2_libmgr` has a THIRD extra the claim does not cover.** Its actual
   list is `{SANDBOX TEST … sg13g2_tests_ase …}` against an expectation with **neither**
   `SANDBOX`/`TEST` **nor** `sg13g2_tests_ase`. `sg13g2_tests_ase` is registered in the
   tracked `ihp-sg13g2/xschem_libs/library.defs:13` and is simply missing from that
   test's expected list — sky130A's sibling expectation *does* list its `_tests_ase`
   lib. So even a perfect cleanup of `SANDBOX`+`TEST` would leave
   `test_ihp_sg13g2_libmgr` red. `test_sky130a_libmgr` and `test_gf180mcud_libmgr` do
   have exactly 2 extras each, as claimed.

The measurer's *classification* (baseline these three, flag the cause, they tell a
verifier nothing) stands. Its *remediation* would not have worked.

### 8.3 `test_gf180mcud_libmgr`'s run-1 failure had a different cause than run 2's

It is correctly HARD — it failed both runs — but in **run 1** it was an X casualty, not a
`library_list` failure. Its entire run-1 output is:

```
Using run time directory XSCHEM_SHAREDIR = .../src
Sourcing .../src/xschemrc init file
X connection to :0 broken (explicit kill or server shutdown).
```

Zero checks ran. Its HARD classification rests on run 2's genuine `library_list` failure
plus its presence in the 2026-08-03 baseline — not on two independent observations of the
same defect. Noted for completeness; it changes no verdict.

Everything else in the structured result — both SUMMARY lines, the 25/16 fail lists, the
