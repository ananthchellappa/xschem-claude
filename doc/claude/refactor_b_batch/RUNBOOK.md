# Refactor B batch runbook — autonomous multi-atom migration harness

*Prepared 2026-07-18. Solves the "one atom per hand-fed session" bottleneck: after atoms 1–25 each
migration was a single generated prompt executed in a fresh session, and a human had to derive the
next task from the audit's RECOMMENDED NEXT line. This harness lets one driver session crank through
20+ plan items — friction-test, implement-or-defer, verify, ledger — with zero human interaction.*

## The pieces

| File | Role |
|------|------|
| `PLAN.md` | **Source of truth.** Ranked ledger of 25+ verbs with checkboxes, per-item scope notes, defer triggers, receipt slots. Written by the phase-0 ranking workflow; updated only by the pipeline's ledger stage (and the driver's preflight/fallback). |
| `atom_pipeline.js` | Per-item workflow script (Workflow tool, `scriptPath`). Stages: Scout → gate → Implement → adversarial Verify (+ one repair) → Ledger. Every stage is a fresh-context agent; the heavy stages never share a context window with the driver. |
| `DRIVER_PROMPT.md` | The main-session loop: preflight, sequential per-item workflow launches driven by completion notifications, stop conditions, final report. Paste into any session to start or RESUME the batch. |
| `prompts/atomNN_<verb>.md` | Implementation prompt generated by each item's scout (atom-26 house style). The scout, not the driver, owns anchor verification. |
| `receipts/NN_<verb>.md` | Per-item receipt: verdict, commit, checks, sabotage results, verifier outcome. |

## Why this shape

- **Fresh context per stage.** Scout, implementer and verifier each get their own window — the exact
  property the manual per-session prompts had, now without the human courier. The driver only ever
  sees small structured receipts, so 20 items don't blow up its context.
- **Friction test is a first-class stage with DEFER as a success outcome.** The atom-24 re-scout
  proved the friction-free pool is EMPTY; most remaining verbs carry F-weight or need a pattern
  unlock. The scout re-verifies the plan's claims from source (the atom-10 lesson: candidate lists
  are overturned by source) and verdicts PROCEED/DEFER against explicit rules. A DEFER records
  *why* — including "needs pattern X" proposals that seed the next contract extension.
- **Strictly sequential items.** Every atom edits scheduler.c, the grep guard and full_audit; the
  implementer builds and runs tests in the shared tree. Parallel items would conflict; the pipeline
  parallelism lives *inside* stages (the verify/repair pair, future multi-lens verifiers), not
  across items.
- **Adversarial verify before the ledger ticks.** Green-but-hollow discipline: the verifier is a
  fresh agent told to trust nothing — it re-runs the atom test, the grep guard and full_audit itself
  and diffs the commit scope. One repair attempt, then [F] and move on.
- **State on disk.** PLAN.md + receipts survive compaction, crashes and session loss. Resume =
  re-paste DRIVER_PROMPT.md; a hung item workflow resumes once via `resumeFromRunId` (cached agent
  prefix replays free), then fails closed.

## Policies (the driver and every stage inherit these)

- **Commits**: launching the batch authorizes ONE commit per green atom (+ fixup commits from the
  repair stage, + one final ledger commit). Explicit file lists only — never `git add -A`,
  `git commit -a`, `git reset --hard` (subagent-git-reset lesson), never push. Commit messages end
  with the atom line + `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>`.
- **Atom numbering**: assigned at launch time as 26 + count of prior `[x]` — deferred items burn no
  number, so the audit's atom sequence stays dense.
- **Baseline fails**: full_audit's ~14 pre-existing WSLg/GUI/WIP fails are recorded verbatim in the
  PLAN.md header at preflight; every verifier compares against that exact list. Any new fail is the
  current atom's problem, full stop.
- **Sabotage-verify**: every named sabotage must fail EXACTLY its target check, be reverted
  (targeted `git checkout -- <file>` after confirming the diff holds only the sabotage), and the
  clean re-run must be green — per atom, no exceptions.
- **Stop conditions**: 20 items processed; two consecutive `[F]`; broken build; unexplained
  non-baseline audit fail. Ambiguity never escalates to the user mid-batch — it becomes a DEFER
  (or an [F]) with reasons, reviewed at the final report.

## Starting / resuming

1. Phase 0 (already run 2026-07-18): produced `PLAN.md`. Re-run it only for a fresh re-ranking
   round after the plan is exhausted (script persisted under the session workflows dir; the method
   is in the atom-24 doc).
2. Start or resume the batch: paste `DRIVER_PROMPT.md`'s prompt block into a session. It preflights
   (build + baseline capture) only when the PLAN.md baseline line is still unfilled, then loops.
3. Watch: `/workflows` shows the live per-item pipeline; receipts land in `receipts/` as items
   complete; PLAN.md checkboxes are the progress bar.

## Known limits / future knobs

- The implement stage is one deep agent per atom. If an atom proves too big for one context, the
  scout should have DEFERred it — that is the friction test working as intended. Splitting the
  implement stage into plan/execute sub-agents is a knob for later, inside atom_pipeline.js only.
- Verifier is single-lens. If hollow-green slips through, widen to the multi-lens refuter panel
  (correctness / does-the-guard-really-trip / scope-creep), majority-kill — a 5-line change in the
  Verify stage.
- Pattern unlocks (T4 items) will mostly DEFER with a proposal. Accepting a proposal (e.g. a
  composite-verb pattern for cut/copy) is a HUMAN decision between batches — fold it into the
  contract, re-run phase-0, go again.
