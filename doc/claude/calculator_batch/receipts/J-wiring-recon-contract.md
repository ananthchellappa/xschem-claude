# recon:contract

### producer_requirements
  - SIZE THE DATABASE EXACTLY. `xschem raw new <db> table <xname> 0 <n-1> 1` yields exactly n points. Forced by `new_rawfile()` (src/save.c): `int number = (int)floor((end - start) / step) + 1;` then `raw->allpoints = number; raw->npoints[0] = number;`. Measured for n = 1, 2, 3, 7, 101: `raw points -1` and `raw points 0` both answer n every time. Consequence the contract states and I confirm by arithmetic: with exact sizing there is NO tail, so a hold-pad loop over [n, allpoints) is an empty range and a zero-padding mutation is unobservable -- the pad branch is dead code. The false diagonal is removed at source, not painted over.
  - NEVER TRUST `raw new`'s RETURN CODE AS 'IT WORKED'. `new_rawfile()` initialises `int ret = 1;` and the create branch never lowers it, so a geometry that allocates nothing still answers 1. Measured on three bad geometries, all rc=1: `0 -1 1` -> `raw points -1` = **0**; `0 -10 1` -> **-9** (the figure the driver quotes, and it comes from THAT geometry, not from the one the suite drives); `0 10 0` (step 0) -> **-2147483647**, i.e. `(int)floor(inf)`. In all three `raw values <xname> 0` is EMPTY and `my_calloc(id, nmemb, size)` returned NULL for `values[0]`/`values[1]` because its body is `if(size*nmemb > 0) { ptr=calloc(...) } else ptr = NULL;`. So success must be confirmed against `xschem raw points`. The shipped producer's `pts != $n` test is STRONGER than `points > 0` and is the right one: it is also what makes the over-allocate mutation unreachable.
  - READ `raw new`'s 0 AS 'THE NAME WAS TAKEN', AND MINT ANOTHER. `new_rawfile()`'s `else { /* file found: switch to it */ ... ret = 0; }` branch switches to the existing slot, applies NONE of the requested geometry and keeps the previous evaluation's samples. Measured: create `__e` at `0 2 1`, write 11.0 into point 0, then ask for `0 9 1` -> rc **0**, `raw points 0` still **3**, `values __e 0` still starts at **11**. A producer that reused one name would freeze the point count at its first call and serve stale data forever. `calc::wave_dest` already does this correctly with a bounded `for {set tries 0} {$tries < 1000}` loop over `__calc_dest$wdestn`.
  - NEVER CALL `xschem raw add <sweepname>` -- IT CLOBBERS THE SWEEP IN PLACE, AND THE EMPTY EXPRESSION DOES IT TOO. In `raw_add_vector()` (src/save.c) the `int_hash_lookup(&raw->table, varname, 0, XLOOKUP)` hit path sets `res = 0`, adds no column, skips the zero-fill, and then `if(expr) plot_raw_custom_data(sweep_idx, 0, raw->allpoints - 1, expr, varname);` writes over the EXISTING column. Tcl's `{}` reaches C as a non-NULL empty string, so `if(expr)` is true. Measured: sweep `0 1 2 3 4`, then `xschem raw add <sweepname> {}` -> rc **0**, sweep becomes `0 0 0 0 0`; with an expression `{<sweepname> 1 +}` -> rc 0, sweep becomes `1 2 3 4 5`. The zeroing mechanism is `plot_raw_custom_data()`'s unconditional `y[p] = (SPICE_DATA)stack2[0];` at the bottom of its point loop with `double stack2[STACKMAX]={0}` and an empty token stream. So the Y column name must differ from the X column name -- `calc::wave_dest` enforces `$xname eq $yname` -> refusal -- and the producer must never hand `raw add` a name the destination already has.
  - `raw set` ONLY EVER TOUCHES THE CURRENT DATABASE, AND A MISS IS SILENT. The `set` arm of the `raw` dispatcher (src/scheduler.c) does `idx = get_raw_index(node, NULL); if(idx >= 0) { ... xctx->raw->values[idx][point] = (SPICE_DATA) atof(argv[5]); ... }` with no else. Measured: with the user's `tran` current, `xschem raw set __wx 0 5.0` returns the EMPTY STRING, raises nothing, and the destination column is untouched (`0 1 2`). So `raw set` cannot report that it wrote nowhere. Worse, with the user's database current, `xschem raw set time 0 999.0` returned `999` and `values time 0` went from `0` to `999` -- a NAME COLLISION WRITES INTO THE USER'S RESULT and fires `annot_data_changed()`. Two requirements follow: the destination must be current for the whole fill (which it is, because `raw new` made it current), and the column names must be ones the user's result cannot have.
  - `ok 1` IS NOT 'THE SAMPLES ARE IN THERE'. `calc::wave_dest` wraps the fill in one `catch` and never reads a sample back, and by the point above a silent `raw set` no-op is not an error. `pts == $n` only proves the GEOMETRY. This is the SR5 exemption working as designed (the producer is in `adders` and in none of the read-back or delete sets), but a stage-J caller must not read `ok 1` as a data guarantee; the only read-back in the tree is band WD6's.
  - CAPTURE BOTH HALVES OF THE REGISTRY CURSOR, NOT ONE. `calc::wave_dest_cur` captures only `extra_idx`'s name+type out of `xschem raw info`. `xschem raw new` then sets `xctx->extra_prev_idx = xctx->extra_idx` (new_rawfile, create branch), and the single `calc::wave_dest_restore` puts back only `extra_idx`. MEASURED on the shipped producer: park the registry at cur=2 prev=0, call `calc::wave_dest` -> cur=2 (right) but **prev=3, the destination**, and `xschem raw switch_back` lands on `__calc_dest<N>`. The tree already has the correct idiom and uses it in `wviewer::trace_cursor_value`: `wviewer::raw_prev_idx` to read prev, `wviewer::raw_cursor_restore {cur prev}` to put the pair back (`switch $prev` then `switch $cur`). See `restore_contract`.
  - NEVER LET THE DESTINATION BE CURRENT WHEN `wviewer::graph_props` CAN RUN. `wviewer::sweep_default` is `[lindex [split [xschem raw list] "\n"] 0]` -- the CURRENT database's first column. MEASURED: with the user's `tran` current, a 3-trace strip with the destination in the middle gives `sweep="time calcx time"`; with the destination current the SAME strip gives `sweep="calcx calcx calcx"` and `sweep_default` = `calcx`. `graph_props` is called by `wviewer::regenerate`, which fires on `add_trace`, on `attach_raw` and on a window `<Configure>`, and its output is written into the rect and persisted. So any `update`, `after` or Tk event while the destination is current can re-axe every ordinary trace on every strip and save that. `calc::wave_dest` closes this window itself by restoring before it returns; a caller that switches to the destination for any reason re-opens it.
  - GIVE `add_trace` THE DESTINATION'S REGISTRY INDEX, OR THE TRACE RESOLVES NOWHERE. The trace needs `rawfile`/`sim_type` keys so `wviewer::db_suffix` emits `%__calc_dest<N> table` into `node=` -- measured `{%__calc_dest1 table}`. Those keys are set only by `add_trace`'s `db` argument path through `wviewer::db_by_index`. And `add_trace` contains `if {[dict get $hit cur]} { set hit {} }`, which DROPS the suffix when the named database is the current one -- a second reason the destination must not be current at `add_trace` time.
  - CONSTRAIN THE X COLUMN NAME TO `wviewer::sweep_token`'s GRAMMAR. `calc::wave_dest` refuses only `{}` and `xname eq $yname`; it accepts whitespace and quotes. MEASURED: `calc::wave_dest {1 2} {3 4} {my x} calcy` returns ok 1 with `xname {my x}`, and `wviewer::graph_props` then emits NO `sweep=` LINE AT ALL (because `sweep_token` returns {}, `strk` falls back to `$swdflt`, and `swany` stays 0). `sweep_token {my x}` and `sweep_token {cal"x}` both answer {}. The trace then silently plots against column 0 of its own database -- accidentally right for a two-column destination, wrong the moment the destination gains a third column. Keep `calcx`/`calcy`, or validate against `[regexp {[\s\"\\]} $name]`.
  - USE `table` AND NOTHING ELSE AS THE sim_type. CONFIRMED end to end, see `results_current_defence`. `raw new` does NOT validate the type (`my_strdup(_ALLOC_ID_, &raw->sim_type, type)` and nothing else), so an invented token registers happily and makes the destination the user's selected result.
  - CALL `calc::wave_dest_drop` -- NOBODY DOES. Derived mechanically over `src/*.tcl` with comments stripped: the ONLY lines naming `calc::wave_dest` or `wave_dest_drop` are the two `proc` definition lines. Zero product call sites for either. Every destination built today is a permanent registry slot.

**restore_contract**: FOUR `xschem raw switch` calls, not two -- and the contract's "TWO explicit switches" is an undercount that I measured leaking. Two reasons force a PAIR, and the pair is needed TWICE.

(1) The by-name arm needs BOTH arguments, and a bare name is a round-robin step. `extra_rawfile()` what==2 (src/save.c):

    if(file && type) { ...strcmp rawfile AND sim_type... }
    else if(file && isonlydigit(file) ) { i = atoi(file); ... }
    else { /* switch to next */
      xctx->extra_prev_idx = xctx->extra_idx;
      xctx->extra_idx = (xctx->extra_idx + 1) % xctx->extra_raw_n;
    }

`ret` is initialised to 1 at the top of the function and that branch never lowers it. MEASURED on the three-slot fixture: `raw switch <path>` answers **rc 1 from every slot** and lands 0->1, 1->2, 2->0. NOT slot 0 -- it is `(cur+1) % n`. So the restore must be `raw switch <name> <type>`, which also happens to be index-independent.

(2) `raw clear` ZEROES BOTH HALVES, which is why the pair is needed a second time. The clear-by-name arm:

        if(found != 0) {
          xctx->extra_raw_n -= found;
          xctx->extra_idx = 0;
          xctx->extra_prev_idx = 0;

MEASURED: user on slot 2 (`op`), `raw new` -> cur=3, `raw clear __c table` -> cur=**0**, and `raw switch_back` afterwards lands on **0**, not on 2. So `switch_back` is not merely a 1-deep toggle after a clear -- it has NOTHING to go back to.

(3) ...and `extra_prev_idx` has to be restored EXPLICITLY, because `raw new` and every `raw switch` overwrite it. `new_rawfile()`'s create branch: `xctx->extra_prev_idx = xctx->extra_idx; xctx->extra_idx = xctx->extra_raw_n;`. MEASURED on the shipped producer: park at cur=2 prev=0, call `calc::wave_dest` -> cur=2 correct, **prev=3**, and `xschem raw switch_back` lands on `__calc_dest<N>`. `calc::wave_dest_restore` restores one half.

So the sequence is:

    capture (cur_name, cur_type) AND (prev_name, prev_type) from ONE `raw info`
      plus one `wviewer::raw_prev_idx` read
    -> raw new -> raw add -> fill
    -> raw switch <prev_name> <prev_type> ; raw switch <cur_name> <cur_type>   (mid-life PAIR)
    -> ... the trace lives ...
    -> raw clear <dest> table            (cur AND prev both forced to 0)
    -> raw switch <prev_name> <prev_type> ; raw switch <cur_name> <cur_type>   (post-clear PAIR)

The order within a pair is prev first, then cur -- that is exactly `wviewer::raw_cursor_restore`, whose own header states the rule ("Order matters: prev first") and whose reader half is `wviewer::raw_prev_idx` (two `switch_back`s, an involution, so it reads without moving anything).

On `switch_back`: `extra_rawfile()` what==5 is `tmp = xctx->extra_idx; xctx->extra_idx = xctx->extra_prev_idx; xctx->extra_prev_idx = tmp; xctx->raw = xctx->extra_raw_arr[xctx->extra_idx];` -- a swap, unusable for nested switches, and after a clear it points at slot 0. Correct to avoid, for those two reasons.

On the "read-only graph getter already clobbers extra_prev_idx" justification: see `contradictions`. It is stale, and the two live reasons above do not need it.

**results_current_defence**: VERIFIED AGAINST CODE AND MEASURED END TO END, and the prior receipt's account is correct.

What `results::current` does (src/results.tcl): `if {[catch {xschem raw loaded} lv]} {return {}}; if {![string is integer -strict $lv] || $lv < 0} {return {}}` then it walks `results::list` for the slot with `cur 1` and `if {![results::_is_result_type [results::_get $r type]]} { return {} }` -- a `return`, not a `continue`, so it answers {} rather than falling through to another slot.

MEASURED, three fixture slots with the user on `op` at slot 2:
 * baseline: `results::current` = `idx 2 ... type op cur 1`, `raw loaded` = 0, 3 slots.
 * after `raw new __r table __rx 0 4 1`: cur=3, **`results::current` = {}**, `results::list` length 4, `raw loaded` still **0**, `raw schname` = the current schematic (new_rawfile stamps `raw->schname = xctx->sch[xctx->currsch]`). So the `raw loaded` gate does NOT defend -- it passes, and the TYPE gate is what returns {}.
 * after `raw switch <fixture> op`: `results::current` = `idx 2 type op cur 1` again. **That is the defence.**
 * after `raw clear __r table`: cur=**0** and `results::current` = `idx 0 type tran` -- the user's `op` selection silently replaced by the `tran` slot. That is the harm the second restore prevents, measured.
 * after the second `raw switch <fixture> op`: back to `idx 2 type op`.

So the driver's hypothesis died exactly as recorded: the odd type does not HIDE the Calculator's slot, it makes the selection UNREADABLE. That is the fail-safe direction (the three decommented consumers of `results::current` in `src/*.tcl` are `calc::ctx_result`, `results::select`'s verdict and `wviewer::selected_rawfile`; the first refuses with `calc::no_result_msg`), but it is a backstop and not the defence. The RESTORE is the defence.

`table` IS the only usable odd type -- CONFIRMED, not refuted, and I drove the whole matrix:

 type        | non_spice | is_digital | _is_result_type | results::current with it current
 ------------|-----------|------------|-----------------|---------------------------------
 table       |     1     |     0      |        0        | {}
 vcd         |     1     |     1      |        0        | {}
 tran        |     0     |     0      |        1        | idx 3 ... type tran cur 1
 ac          |     0     |     0      |        1        | idx 3 ... type ac cur 1
 op          |     0     |     0      |        1        | idx 3 ... type op cur 1

 {}          |     0     |     0      |        1        | idx 3 ... type <NULL> cur 1

`raw_reader_table[]` (src/save.c) is literally two rows -- `{"table", table_read, 0}, {"vcd", vcd_read, 1}` -- and `raw_type_is_non_spice()` returns 0 for a NULL or empty type. `my_strdup()`'s header says "empty source string --> dest=NULL", so `raw new nm {} ...` leaves `sim_type` NULL, `raw info` renders it `<NULL>`, and `results::_is_result_type` maps `{}` and `<NULL>` to 1. An INVENTED token is the dangerous case the contract does not spell out: `raw new` does not validate the type at all, so `calcscratch` registers and becomes the user's selected result.

`results::list` lists the destination either way: measured row `idx 3 type table cur 0 label {__lab (table)} path {__lab}`. `wviewer::db_label` builds that label as `<tail> (<type>)`. So it appears in Results > Select whatever its type -- declared, not fixed.

**throw_hygiene**: THERE IS NO CLEANUP PATH TODAY, AND THE HOLE IS BIGGER THAN "declared unfenced" SUGGESTS -- BUT NARROWER THAN "the user is stranded".

What leaks, measured. Three consecutive `calc::wave_dest` calls with the caller raising immediately afterwards and nothing dropping:

    inv = 0:calc_fixture.raw:tran 1:calc_fixture.raw:op 2:__calc_dest1:table
    inv = ... 2:__calc_dest1:table 3:__calc_dest2:table
    inv = ... 2:__calc_dest1:table 3:__calc_dest2:table 4:__calc_dest3:table
    results::list labels = {calc_fixture.raw (tran)} {calc_fixture.raw (op)}
                           {__calc_dest1 (table)} {__calc_dest2 (table)} {__calc_dest3 (table)}

One permanently registered, never-freed `table` slot per failed evaluation, each one a `Raw` plus two `SPICE_DATA` columns, each one a row in the Results > Select picker. `xctx->extra_raw_size` grows by 20 whenever `extra_raw_n` reaches it. And every `__calc_tmp*` leak row elsewhere in the batch reads `xschem raw list`/`raw info`, so a leaked orphan changes the inventory those rows measure.

What does NOT leak: the user's current slot. `cur` stayed 1 (`op`) and `results::current` still answered `type op` across all three leaks, because `calc::wave_dest`'s mid-life restore runs before the proc returns. So the "left the user on the Calculator's own scratch database" framing of hole H8 is wrong for a throw out of the CALLER; it is right only for a throw out of the producer between the create and the restore, and I could find no such window: every exit path below the create calls `calc::wave_dest_restore` BEFORE `calc::cross_msg` and the dict build, the fill is inside one `catch`, `calc::wave_dest_cur` and `calc::wave_dest_restore` are both internally catch-guarded, and `dict create` cannot throw.

Two paths that DO strand the user, neither of them a throw, both measured:

 (a) A USER SLOT WITH A `<NULL>` sim_type CANNOT BE RESTORED, SILENTLY. `calc::wave_dest_cur` returns `{__nullty <NULL>}`; `calc::wave_dest_restore` then issues `xschem raw switch __nullty <NULL>`, which can never match because `extra_rawfile()`'s by-name loop requires `xctx->extra_raw_arr[i]->sim_type` non-NULL before it compares. Measured: user on slot 1 (`<NULL>`), after `calc::wave_dest` ok=1 the user is on slot **2, the destination**, with `prev {__nullty}` / `prevtype {<NULL>}` in the answer dict. `calc::wave_dest_restore` returns the verb's rc and NOTHING READS IT -- its own header even says "Answers the verb's rc, which says nothing about where it landed".

 (b) WITH NOTHING LOADED THE DESTINATION IS LEFT CURRENT. `raw info` is empty (its arm is `if(xctx->raw)`), `calc::wave_dest_cur` returns {}, `calc::wave_dest_restore` returns 0 without switching. Measured: `inv = 0:__calc_dest5:table`, `raw sim_type` = `table`, `results::current` = {}. In the click path `calc::fn_measure` runs `calc::require_result` first, so this is only reachable by a direct caller -- but stage J must not introduce one.

The one leaked thing that reaches the user visibly: `extra_prev_idx` is left on the destination after every successful `calc::wave_dest` (see `restore_contract`), so `xschem raw switch_back` -- the documented idiom -- lands on `__calc_dest<N>`.

What a correct stage J owes: wrap the whole producer-plus-plot sequence so that `calc::wave_dest_drop` runs on every exit path including a raise (Tcl 8.6 `try ... finally`, or the `catch`-then-restore-then-rethrow shape `wviewer::signal_list_all` already uses), and either refuse when `calc::wave_dest_cur` answers {} or treat a non-1 `calc::wave_dest_restore` rc as a failure.

### traps

The short-list defect needs a hand-edited rect, an `xschem setprop`, or a state file from another build. Band WD4 asserting the positive shape upstream of all the walkers is the right fence and remains so.
  - ...BUT THERE ARE **NINE** READERS OF THE `sweep=` TOKEN, NOT SEVEN, AND THE TWO MISSING ONES ARE IN `callback.c`. Derived with `/usr/bin/grep -n '\"sweep\"' src/*.c` and each line mapped to its enclosing symbol: `graph_fullxzoom`, `graph_fullyzoom`, `find_closest_wave`, `graph_point_at`, `wave_hilight_envelope`, `graph_wave_resolve`, `draw_graph` (src/draw.c) plus `backannotate_cursor_b_in_db` and `waves_callback` (src/callback.c). The reachable defect family for stage J is the first-token one, not the carry-forward one.
  - A DESTINATION TRACE **ALONE ON A STRIP** IS THE DANGEROUS POSITION, WHICH IS THE OPPOSITE OF WHAT §9 SAYS. `wviewer::plot_signals`/`add_trace` APPEND, so a destination plotted into an empty strip is trace 0 and `calcx` becomes the FIRST `sweep=` token. Then: `waves_callback` computes the strip's whole mouse-to-X mapping from `get_raw_index("calcx")` resolved in the CURRENT (user's) database -> -1 -> `idx = 0` -> `get_raw_value(dset, 0, ...)`, i.e. the X scale and every mouse X on that strip come from the user's `time` column, not from `calcx`; `backannotate_cursor_b_in_db` does the same for the values it writes onto the schematic. Conversely with the destination in the MIDDLE (what §9's fence demands) the first token is `time` and both are right -- so §9's middle rule is a product requirement as well as a fence-design one, and the contract presents it as only the latter.
  - AUTO X ZOOM CANNOT SIZE A MIXED STRIP, BY DESIGN, SO THE DESTINATION CAN BE DRAWN OUTSIDE THE WINDOW. `graph_fullxzoom` passes its single first `sweep=` token down to `graph_x_union_rect`, which switches into each trace's own database and calls `graph_x_extent(sweep_name, ...)`. That function contains `if(idx < 0) return 0;` with the comment "A database that does not HAVE the target strip's x quantity has no extent IN that quantity, so it contributes nothing". On a mixed strip (first token `time`) the destination has no `time` and contributes NOTHING to the X union; on a destination-only strip (first token `calcx`) the user's database contributes nothing and the zoom is correct. Either the destination gets its own strip or Full-X-zoom ignores it.
  - A CYCLE-NUMBER X AXIS AND A TIME X AXIS SHARE ONE NUMERIC X RANGE ON A STRIP. `gr->x1`/`x2` are per-RECT, and the cursor position handed to `wviewer::interp_value` is in the strip's units. R420's `number` mode produces 1, 2, 3 beside a `time` trace spanning 0..4e-3. Nothing refuses the combination; it is simply incoherent.
  - `raw add <yname> {}` DOES NOT MEAN "add an empty column" -- IT RUNS THE RPN ENGINE. Tcl's `{}` arrives as a non-NULL empty string so the scheduler takes the `argc > 4` branch and `raw_add_vector` calls `plot_raw_custom_data(0, 0, allpoints-1, "", yname)`, whose unconditional `y[p] = (SPICE_DATA)stack2[0];` writes zeros (benign only because `stack2` is `={0}`). `xschem raw add <yname>` with no fourth argument takes the `expr == NULL` branch and gives the identical result -- measured, both zero-filled. Worth knowing because the `{}` spelling is the one that clobbers a sweep.
  - `raw clear` WITH NO ARGUMENT CLEARS THE USER'S RESULT AND EVERYTHING ELSE. Measured: 3 slots with the user on `op` -> `xschem raw clear` -> rc 1, 0 slots, `raw loaded` = -1, `extra_raw_arr` freed. The cleanup must always be `raw clear <dest> <type>`; a `$db` that came back empty and an unguarded `xschem raw clear $db` would be exactly this. `calc::wave_dest_drop` guards it (`if {$db eq {}} { return 0 }`), and that guard is load-bearing.
  - `raw clear <name> <type>` COMPACTS THE ARRAY (`xctx->extra_raw_arr[i - found] = xctx->extra_raw_arr[i]`), so an index-based restore is safe ONLY because the destination is appended LAST and nothing after it shifts. Hole H4's claim is correct as stated, and it stops being correct for any producer that clears something other than the newest slot.
  - `xschem raw points 0` NEEDS `dset < raw->datasets`; OUT OF RANGE IT SETS NO RESULT AT ALL. The arm is `if(dset >= 0 && dset < raw->datasets) Tcl_SetResult(...)` with no else, and the whole block sits behind `else if(raw && raw->values)` which falls through to an empty result when nothing is loaded. So the honest check is `[string is integer -strict $pts] && $pts == $n` -- which is what `calc::wave_dest` does. A bare `$pts > 0` on an empty string is a Tcl error.
  - THE DESTINATION BEING REGISTERED MOVES THE REGISTRY CURSOR ON EVERY CURSOR MOTION. `wviewer::trace_cursor_value` switches into the trace's own database once per trace per motion and restores the pair with `wviewer::raw_cursor_restore`. For the window of each call `results::current` answers {}.
  - NOTHING VALIDATES THE sim_type PASSED TO `raw new`. `new_rawfile` just `my_strdup`s it. Measured: `calcscratch` registers and `results::current` reports it as the user's selected result. The `table` choice is load-bearing and must not be made a variable.
