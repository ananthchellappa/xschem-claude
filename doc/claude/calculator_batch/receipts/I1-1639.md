## 4. The disposition decision — option **1**, defer behind the shared sentence

**Decided: (a) defer.** The two arguments that settled it, in order of weight.

**1. The request is WELL FORMED, so there is nothing for D7 to refuse.** The issue's case for (b)
rests on *"a transition time between two specific crossings has no meaning for all of them"* — and
that does not survive the proc's **own published** meaning of `nth`, which its header states: `nth`
selects the **low** crossing, and the high one is **derived** as the first crossing strictly after it
(T2). So `nth` 0 names **exactly one rise time per low crossing**: a wave with its own X axis, with no
ambiguity about which pair is meant. That is the identical shape `calc::dutyCycle`'s `cycle` 0 already
answers, and the shape `calc::wave_dest` exists to hold. D7 refuses a request that cannot be
**interpreted**; this one can be.

**2. A D7 refusal would have to be REVERSED as user-visible behaviour.** Once R410/R412's argument
dialog can route a wave into `calc::wave_dest`, this request gets an answer. A refusal saying it
cannot be interpreted would then be a false statement the batch has to retract; a deferral retires
silently, which is precisely why the sentence is shared ("a landing destination retires one string
rather than one per caller").

**3. `calc::delay` is the precedent and not an analogy.** It is also a measurement proc with **no
`_scalar` wrapper**, it also takes an `nth` on `cross`'s contract, and it defers **inside itself** —
so putting the guard in `riseTime` itself is the family's existing shape for exactly this situation,
not an improvisation. (`cross` and `dutyCycle` answer the wave in the proc and defer in a `_scalar`
wrapper; `riseTime` has no wrapper to put it in, and inventing one plus a `sweep` series would be a
new user-visible answer no ruling covers.)

**4. It is mechanically free.** `MT7`/`MT8` compare by identity and count no users; `WD9` pins the
sharing by name. No new `cross_msg` kind was minted, so **no new user-visible sentence** was
introduced and there is nothing here for the driver to file a wording ruling about.

**The ordering inside the proc is a second decision and it is fenced.** The guard sits **after** every
request-level check — the swing, both references, both percentages, the zero swing — and before any
threshold arithmetic. Reason: a deferral promises an answer once a destination lands, and a request
with no swing will **still** be malformed then, so a malformed request is refused *as malformed*
rather than deferred. Nothing in any contract states this, so `MT9b` states it with a row, and moving
the guard to the top of the proc reddens exactly that row (sabotage 5).

## 8. What I got wrong, and holes I am declaring

**Wrong, and what corrected me.**

1. **I wrote `v2` into the issue stamp.** `issue_stamp.tcl` rejected it immediately —
   *"first token must be the schema version `v1`"*. The `v` field is the **schema** version, not the
   revision of the claim. Corrected before anything else ran.
2. **I wrote a malformed `if` in my own arm-sweep probe** (`[regexp … -> k}` with the `]` missing) and
   xschem answered *"missing close-bracket in expression"* at startup. Harmless, but it is the same
   family as the warning this batch keeps re-learning: Tcl's brace counting ignores a backslashed
   brace, so the eye checks braces and misses brackets.
3. **I first planned the band as `MT11` placed after `MT10`.** That would have put new rows *after*
   `MT10`'s whole-suite `R402` row, silently narrowing a claim that covers every exit path every band
   above it drove. Re-read `MT10`'s last row and moved the band.

**Holes.**

* **H1 — the catalogue entry stays `returns scalar`, deliberately.** `riseTime` still answers one
  number today; it *defers* the wave rather than producing one, exactly as `calc::cross_scalar` does.
  Changing the entry to `scalar/wave` would be user-visible metadata with no behaviour behind it and
  would redden row `S24` of `test_calc_skeleton`. **When the click routes `nth` 0 into
  `calc::wave_dest`, that entry becomes `scalar/wave` and `S24` is where it lands.** Unfenced by
  construction: there is no row asserting that it *should not* be `scalar/wave` yet.
* **H2 — `nth` 0 for `riseTime` now has no answer at all**, only a better-behaved refusal. The wave it
  describes is not computed anywhere. PLAN 5.4's dialog plus `calc::wave_dest` is what pays it off.

* **H4 — the four documentation corrections in §5 touch files outside the two the brief assigned me.**

## 9. What the next stage must know, including where a brief claim is wrong

1. ⚠ **MY BRIEF SAID THE CONCURRENT CREW "WILL NOT WRITE", AND IT WROTE.** `CLICK_CONTRACT.md` gained
   a new **§8** ("the dialog, specified from the two modals this tree already has") *during* my stage.
   My own §6 note and their §8 are both present and intact, so nothing was lost — **but that was luck,
   not safety.** My edit was a read-modify-write of the whole file in a separate process; had their
   append landed between my read and my write, I would have silently clobbered a design crew's entire
   section with no conflict and no error. **Two crews must not be told a shared document is
   single-writer unless it is enforced.** Append in place (`>>`) or hand the edit to the driver.
2. ⚠ **A DRIVER/ISSUE CLAIM IS TOO STRONG, MEASURED BY SABOTAGE 4.** Both my brief and issue 1639 say
   *"splitting that sentence per caller reddens MT7 and MT8."* It does **not**, for the split that
   actually matters here. `MT7` and `MT8` read **`delay`'s** and **`dutyCycle_scalar`'s** answers, so
   they redden on a split that changes the sentence **the siblings** use. A split that gives only a
   **new** caller its own wording sails past both — it is caught by `MT9b`'s identity row and by all
   three `WD9` rows instead. **Both routes are fenced, in different files**, and a dialog author told
   only about MT7/MT8 would be checking the wrong suite. The refinement is recorded in
   `CLICK_CONTRACT.md` §6 and in `NUMBERING.md`.
3. **`WD9`'s derived caller set has now delivered once**, which is the strongest argument in the tree
   for deriving a set rather than listing it: it reddened on the first run after the fix, naming the
   caller nothing was driving, and the correct remedy was to drive it. Any **fifth** deferring caller
   reddens there the same way. **Do not relax it.**
4. **`calc::delay` and `calc::riseTime` are now the two layered verbs that defer inside themselves**,
   with no `_scalar` wrapper; `cross` and `dutyCycle` defer in a wrapper and answer the wave in the
   proc. Both shapes are legitimate and the difference is whether the verb has a wave answer to give.
   `frequency` and `period_jitter` will have one, so they want the `_scalar` shape.
5. **The guard spelling is now in four places** and they are byte-identical by intent
   (`calc::cross_scalar`, `calc::delay`, `calc::dutyCycle_scalar`, `calc::riseTime`). Nothing derives
   that set except `WD9`, which derives it from the `listdefer` *call site* and not from the guard —
   so a fifth caller that got the guard wrong would still appear in `WD9`'s set. If that matters, the
   row to write is one deriving the **guard** shape, and it does not exist.
