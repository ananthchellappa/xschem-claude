Debugging case study · X11

The Fatal Hint

A schematic editor could take down every window on the machine — not its own window, every window — by asking the X server, politely, for a favour it never needed.

XSCHEM · issue 0413 VcXsrv 21.1.16.1 Reading time ~15 min

Here is a bug report, in full: “Pressing Ctrl-B in the waveform viewer kills the X server.”

Not crashes the app. Not throws an error. The X server — the process that owns the screen, the keyboard, the mouse, and every window belonging to every program — dies, and has to be restarted by hand. Every other application on the desktop dies with it. One keystroke in one program, and the building comes down.

This walkthrough is the whole investigation: the hypothesis that was wrong, how it was killed, how the crash was reproduced without destroying the reporter's desktop, and the one word that turned out to be the cause. Almost none of the useful parts are specific to X11. They are the same moves you will make on any bug where the failure happens somewhere you do not control.

01 Why this report is extraordinary

Start with why an experienced engineer should sit up at that sentence, because the reaction is the first piece of analysis.

X11 is a client–server system, and an old one — the protocol is from 1987. Your applications are clients. They own no pixels. They open a socket to a server, which owns the display hardware, and they send it requests: CreateWindow, ConfigureWindow, CopyArea. The server is shared infrastructure. Dozens of mutually distrustful programs are connected to it at once.

The analogy to keep

The server is the landlord; the clients are tenants. Tenants ask for things — a repaint, a bigger room, hold my mail. The landlord may agree or refuse. What must never happen, no matter how strange the request, is that one tenant's paperwork burns down the building. If it does, the fault is not only in the tenant who filed it.

This is a trust boundary. The server's contract with every client is that a malformed request earns an error, not a death. That contract is why servers validate: the protocol defines BadValue, BadMatch, BadWindow precisely so that nonsense from one client is reported to that client and survived by everyone else.

So a client that kills a server means one of two things, and probably both: the client is sending something malformed, and the server is mishandling it. Hold both suspicions. Do not resolve them early.

02 The obvious suspect, and its alibi

There was already a leading theory when the investigation started, and it was a good one. Worth walking through, because killing a plausible hypothesis quickly is most of what debugging is.

Ctrl-B opens a “signal browser” — a panel listing every signal in a simulation. It lays names out in columns and sets the scrollable region to columns × columnWidth. And here is the thing every X programmer eventually learns: X11 coordinates are signed 16-bit. Every x, y, width and height on the wire lives in −32768…32767. A simulation with enough signals makes that product enormous, and a number that does not fit is exactly the sort of thing that could make an old server misbehave.

Clean theory. It names a mechanism, it predicts the trigger scales with signal count, and it is falsifiable. So falsify it. Two measurements, both cheap:

  • Build a bare Tk canvas with a scroll region 150,096 pixels wide and 848 items placed out to x = 150,000, and scroll it end to end. The server did not care. No error, no death.
  • Instrument the real panel on the reporter's actual data — 424 signals, the very file that crashed it — and print the numbers it computes. Result: cols=3 colw=88, scroll region 264 pixels. Not 32,767. Two hundred and sixty-four.

The suspect had an alibi. There was a second one already on record: the reporter had upgraded the X server from a 2020 build to the current one before this investigation, hoping that was it, and the crash was unchanged. That kills ancient server as an explanation too — and, importantly, it moves the blame toward us. A six-year-old server mishandling a legal request is a story about the server. A current server dying the same way says the request itself is wrong.

Method

A hypothesis that survives because nobody measured it is not evidence, it is a rumour with a citation. Both of these took minutes and each removed a whole branch of the search tree. Cheap falsification first, always — and notice that the strongest thing the 16-bit theory had going for it was that it was the first one written down.

03 Reproduce it without burning the reporter's house down

Now a practical problem that comes up constantly and is rarely taught: the act of reproducing this bug destroys the environment you are working in. Every crash costs the reporter their entire desktop. You cannot iterate that way, and you certainly cannot ask someone else to.

The move is a stunt double. The X server is not a singleton — you can run a second one on a different display number, point one client at it, and crash it as often as you like while the real screen carries on. That second instance was launched with verbose logging turned on, which the everyday one is not:

vcxsrv.exe :11 -multiwindow -clipboard -wgl -ac \
    -logfile C:\...\vcx11.log -logverbose 3

This buys three things at once. Isolation: only the sacrificial server dies. Iteration: crash it fifty times, nobody notices. And observability — the everyday configuration produces no log at all, so the single most valuable artifact in the whole investigation only exists because the repro was staged deliberately.

First run of the real gesture against it: the client printed X connection broken, and the server's log ended here.

Using Composite redirection
winMultiWindowWMProc - Error code: 8 (Match), ID: 0x180000,
                       Major opcode: 12 (ConfigureWindow)

Read that line slowly, because it reframes the entire problem. Major opcode: 12 is ConfigureWindow — move/resize a window. Error code: 8 is BadMatch. And winMultiWindowWMProc is not our code and not our thread. It is a thread inside the X server.

Notice what this does to the search. We are no longer looking for the malformed request XSCHEM sent. We are looking for the state XSCHEM put a window into that made the server's own manager generate a request it could not satisfy. Different question, different evidence.

04 Twenty questions, played properly

The crashing function builds a whole panel: a paned window, a tree, a search bar, a canvas, a scrollbar. Dozens of candidate culprits. This is where beginners start reading code and experts start bisecting.

Delta debugging is binary search applied to a failing scenario: cut the input in half, ask which half still fails, repeat. It is the same algorithm as twenty questions, and it has the same property — each answer halves the world, so twenty questions is enough to find one item in a million.

The panel's construction was cut into eight numbered stages, run one at a time, with the sacrificial server restarted between runs. The answer arrived on the first stage. The crash was not in the tree, the scrollbar, the fonts or the layout maths. It was the very first statement, before the panel had drawn a single pixel:

pack $sidebar -side left -before $drawingArea

One line of layout. Now widen instead of narrowing — having found a trigger, map its edges, because the shape of the boundary is what names the mechanism:

Every row is the same binary, the same server, one gesture changed. The pattern is unambiguous: what matters is not how big the window becomes, but whether its origin moves.

Two conclusions fall straight out. First: the signal browser was never the bug. It was one caller of a gesture that any left-hand or top sidebar performs, on any window in the program. The feature in the bug report was a witness, not a suspect.

Second, and this is the pivot: plain Tk doing the identical thing does not crash. So the difference is not the gesture. The difference is something about our window that a stock one does not have. That reduces a huge search to a small, answerable question: what do we set on that window that nobody else does?

One attribute, set once at startup, in one line of C:

winattr.backing_store = WhenMapped;
Tk_ChangeWindowAttributes(tkwindow, CWBackingStore, &winattr);

05 The control group

A suspect is not a conclusion. At this point there was a strong story and zero proof, and the gap between those is where wrong fixes get shipped.

So: a controlled experiment, in the sense your biology teacher meant. One binary. One environment variable that flips that single attribute and nothing else. Two runs, same gesture, back to back:

The one-variable A/B. Same executable, same server, same keystroke — only the attribute differs. Then the original bug report's exact path, on the real 424-signal session, with the attribute off: survives.
Attribute requestedOutcome
backing_store = WhenMappedserver dies, every time
backing_store = NotUsefulsurvives, every time

That is the difference between I believe and I measured. It costs one conditional and ten minutes, and it is the only thing standing between a real root cause and a plausible story that happens to correlate. Keep the knob afterwards, too — the escape hatch that produced the control group is also how the next person reproduces the bug on purpose.

06 What backing store actually is

So what was that one word doing?

When a window is covered and then uncovered, the pixels underneath have to come from somewhere. There are two ways to arrange that. Either the client keeps its own copy and repaints on demand, or it asks the server to remember the covered pixels on its behalf. That second thing is backing store.

The analogy to keep

Backing store is asking the building's concierge to hold a spare copy of your keys. It is a request, not a contract. The concierge may agree, may forget, may have a policy against it — and crucially, the protocol says so out loud: backing store is a hint. A conforming server is free to ignore it entirely, and many do.

This distinction — hints versus guarantees — runs through all of systems programming, and it is one of the most reliable places for bugs to hide. A cache Expires header, a madvise() call, a scheduler nice value, a query planner index hint: advisory. You may not rely on the answer. And because you may not rely on it, you must already have a fallback that works without it.

Which raises the question that decided the fix. If the hint is ignorable, what does this program do when it is ignored? It turns out: exactly the right thing, and it has been doing it since 2017. The application double-buffers all its drawing into a pixmap it owns, and on every expose event it copies from that buffer back to the window. There is even a comment sitting next to the code:

/* redraw selection on expose, needed if no backing store
   available on the server 20171112 */

So the fix is one word, from WhenMapped to NotUseful, and the reason it is a fix rather than a workaround is the paragraph above: we were not disabling a feature we relied on. We were withdrawing a request whose answer we had never once used.

A test worth applying to your own code

Find the optimisations in your system that are advisory. For each, ask: what breaks if it is ignored? If the answer is nothing, you are carrying a dependency with no benefit — pure risk surface. If the answer is I don't know, that is the more interesting finding, and it means the fallback path has never been exercised.

07 Whose bug is it?

Both parties. Say so plainly, and resist the pull to pick one.

Ours, because we requested a hint we did not need, and on this platform that request had a fatal side effect. That is squarely fixable by us, so we fixed it — and the users on affected setups get relief immediately rather than after an upstream release cycle.

Theirs, because nothing a client asks for may kill an X server. Look again at what the server did: its internal window manager made a request, got an error back, and treated that error as unrecoverable. Fail-fast is a virtue in a component and a catastrophe in shared infrastructure. A crash is a fine response to a broken invariant inside a single process. It is never a fine response to input from an untrusted peer — and every one of the server's clients is an untrusted peer.

The analogy to keep

The landlord received a form he could not process and, rather than filing a complaint, demolished the building. That the tenant's form was odd does not make the demolition reasonable. Both findings are real, and reporting only the one you can fix is how the other one survives to bite the next person.

There is a well-known piece of advice hovering here — be conservative in what you send, liberal in what you accept, sometimes called the robustness principle. It has aged badly as a rule about parsing, where quietly accepting garbage propagates it. But its second half holds absolutely at a trust boundary in one specific sense: accepting input you dislike must never mean dying because of it. Reject it, log it, disconnect that client if you must. Do not take everyone else down with you.

08 The test you cannot write, and the one you can

Last act, and for a working engineer it is the most useful one. A bug is not finished when it stops happening. It is finished when it cannot come back unnoticed.

Except here you cannot test for it. The crash needs a specific X server, driving a real display, on a specific operating system. The project's automated tests run headless, on virtual servers — and those servers tolerate the exact gesture that kills the real one. Fourteen test suites covered this feature and every one of them passed, throughout.

The analogy to keep

The streetlight effect: the drunk searches for his keys under the lamp-post, not because he dropped them there, but because that is where the light is. Headless CI is the lamp-post. It is genuinely where most bugs are findable — and it is worth knowing, explicitly, which parts of your system are permanently outside the circle of light.

So separate two things that are easy to conflate: the consequence (the server dies) and the request (we set an attribute). The consequence is untestable here. The request is entirely ours, is one word, and is the whole of the defect. Assert on that instead.

The regression test asks the running program what attribute its windows actually carry, on the main window and on a second window created later — because the code sets it in three places, and a fix applied to only the startup path would leave every new window crashing. Then the part that matters most:

$ XSCHEM_BACKING_STORE=1 ./xschem --script test_backing_store_0413.tcl
FAIL: BS4 the MAIN drawing window carries NotUseful -> {WhenMapped}
FAIL: BS5 a NEW drawing window carries NotUseful too -> {WhenMapped}

That is the escape-hatch knob from step 05, reused as a negative control. A test that has never been observed to fail is not yet known to be a test — it might be asserting nothing at all, and green forever either way. Making it fail on purpose is how you learn it is wired to reality.

09 What to carry away

Almost none of this was about X11. Strip the protocol out and the moves are portable:

  1. Falsify the leading theory first. It is leading because someone wrote it down first, which is not evidence. Two measurements retired a whole branch of the search here, and one of them was a number — 264, where the theory needed 32,767.
  2. Stage the reproduction so you can afford to repeat it. If observing the bug destroys the environment, build a sacrificial one. Cheap repetition is what makes every later step possible.
  3. Get the log from the layer that actually failed. The decisive line came from inside the other process. Everything before it was speculation; everything after it was arithmetic.
  4. Bisect the scenario, not the source. Delta debugging found the guilty line in one step, in code nobody had read yet.
  5. Then widen, to find the edges. Narrowing gives you a trigger. Mapping the boundary — moves crash, resizes don't — gives you the mechanism, and told us the reported feature was innocent.
  6. Change one variable. The A/B on a single binary is the difference between a correlation and a cause, and it is almost always affordable.
  7. Know which of your dependencies are hints. Advisory means the fallback must exist. If nothing breaks when the hint is ignored, you are holding pure risk.
  8. At a trust boundary, dying is not an error-handling strategy. Fail-fast inside a process; fail-safe at the door.
  9. Report both bugs. Fix your side because it helps users now; file theirs because the next person to hit it will not have this write-up.
  10. When the consequence is untestable, test the request. And prove the test can fail before you trust its green.

The fix is one word in src/xinit.c. Finding out that it was one word took a second X server, eight bisection stages, a controlled A/B, and one line of somebody else's log file.
