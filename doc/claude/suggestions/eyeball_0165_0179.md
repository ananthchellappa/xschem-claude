## 1 — 0165: the warning

```sh
/home/qflow/dev/xschem/claude_1/xschem/src/xschem \
  --rcfile /tmp/xschem_0165_eyeball/xschemrc \
  /tmp/xschem_0165_eyeball/eyeball_0165.sch
```

The canvas carries its own instructions. Press the **Netlist** button.

The design is the smallest honest version of the bug: `hidden_supply.sym` takes
its supply as an `extra=` attribute (upstream's documented "hidden pin" idiom),
instance `X1` binds `VCCPIN=#vdd_typo`, and the wire on the right is **labelled**
with the same spelling. They are not the same node.

**Expect three things.**

1. **The new warning**, in the ERC Info window:

   > `Warning: instance: X1: attribute VCCPIN=#vdd_typo binds a node whose name
   > starts with '#', which is reserved for auto-named nets: the binding reaches
   > the netlist verbatim while a wire labelled the same way is stripped, so the
   > two are DIFFERENT nodes`

2. **The old label-side warning still there**, in the same transcript:

   > `Warning: instance: lH: net name '#vdd_typo' starts with '#', which is
   > reserved for auto-named nets`

   Both halves of the trap get reported. Leg HW3 pins this, because "the label
   half is already covered" is the reason the pin-name half of 0165 was left
   without a warning of its own — if that ever stops being true, the argument
   expires silently.

3. **The netlist is unchanged.** `File > Edit Netlist`, or open
   `/tmp/xschem_0165_eyeball/eyeball_0165.spice`:

   ```
   X1 topn #vdd_typo hidden_supply     <- the binding, verbatim
   R9 vdd_typo GND 1k                  <- the same spelling, '#' stripped
   ```

   Two nodes, from one name. That is the defect, and D1 was "warn, don't
   rewrite", so it is still there on purpose. The warning is the only new thing.

## THE OPEN QUESTION — add the canvas highlight for parity?

**You will notice this within seconds of the first eyeball**, so it is written
down rather than left to be rediscovered.

The existing label-side warning does two things, not one
(`src/netlist.c:1491-1500`):

```c
        statusmsg(str,2);
        inst[i].color = -PINLAYER;      /* :1498 */
        xctx->hilight_nets=1;           /* :1499 */
```

— it writes to the ERC window **and highlights the offending instance on the
canvas**. The new binding warning only does the first. So on `eyeball_0165.sch`
the `#vdd_typo` label lights up and `X1`, which is the instance actually carrying
the bad binding, stays plain.

That asymmetry is not deliberate design; it is scope discipline. Adding it was
not part of what was approved (D1-D4 were about whether to warn at all), and it
changes drawing state, so it was left out and recorded here instead.

**Recommendation: yes, add it — but measure first, because it is probably not a
two-line copy.** The reason:

- `netlist.c:1491` fires inside `name_nodes_of_pins_labels_and_propagate()`,
  during `prepare_netlist_structs()`, on the `xctx->inst[]` array of the cell
  being prepared.
- `warn_hash_extra_node()` fires inside `print_spice_element()`, during
  **emission**. For a child cell, that `xctx->inst[]` is discarded when the
  hierarchy walk returns; and `spice_netlist.c:533-534` re-runs
  `prepare_netlist_structs()` on the reloaded top afterwards.

So a colour set at emission time may be thrown away before anything is drawn, and
may or may not survive for a top-level instance. Before writing the two lines:
set the colour, netlist the fixture, and **look at whether X1 actually
highlights** — in both arms (top-level instance and an instance one level down).
If it does not survive, the honest fix is to move the check, not to leave a
no-op assignment in the emitter.

If it turns out to need moving, the alternative shape is a second pass in
`prepare_netlist_structs()` that resolves `extra=` bindings the way
`print_spice_element()` does — which is real work and should be its own issue,
not a bolt-on.

**A cheaper half-measure worth considering either way:** the warning names the
instance (`instance: X1:`) but there is no way to jump to it. `Ctrl+Shift+G`
(the find helper) can select by instance name, so the information is reachable —
just not in one click.

## Second, smaller question: should an ERC warning pop the window at all?

`show_infowindow_after_netlist` defaults to `onerror` (`src/xschem.tcl:15552`),
and an ERC **warning** does not set `err`. So in a normal session the Info window
*updates* but does not *appear*. The fixture's `xschemrc` sets `always` purely so
the eyeball is unambiguous.

This is pre-existing behaviour and 0165 did not change it — the label-side
warning has always behaved the same way. But it does mean a user who never opens
`View > Show / Hide > Show ERC Info window` will not see either warning, which is
worth weighing against the whole premise of "warn rather than rewrite". There is
no GUI control for the variable today; it is rc-only.

Not changed, because it is a global default affecting every warning in the tool,
not a 0165 decision.
