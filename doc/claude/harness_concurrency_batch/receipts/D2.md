## The `src_line`-first-match trap — how I ruled it out, three ways

The brief warned this is the way the task can do silent damage. It is ruled out by
mechanism, by provenance, and by an adversarial control.

**1. Mechanism — no row reads this file.** Every text this suite reads, enumerated from
the source rather than assumed (`grep -nE 'slurp |file copy|open \[|\[spit'`):

| rows | haystack |
|---|---|
| S3a, S1×3, S2×3 | `$SRC(open_close/create_save/netlisting)` — `tests/<case>.tcl` |

`test_regression_concurrency_1476.tcl` appears in **none** of them. Line 112 is the
`slurp` *proc definition*, not a call.

**2. Provenance — the values the rows now print cannot have come from here.**
`grep -cF` of each newly reported source value, in my file vs the file the row reads:

```
  suite=0  other=2  <- $testname/results.[pid]      (S2's quote)
  suite=0  other=1  <- set lock_file                (V1a's quote)
  suite=0  other=1  <- REFUSING TO RUN              (V2a's quote)
```

Three of the five are **absent from this file entirely**, so they are proof by
provenance. The two that are present are pre-existing comments (`:59` and `:38`), which

**3. Adversarial positive control — the B1 failure mode, reproduced deliberately.** I
inserted an inert braced string at the **top** of the file (line 109, ahead of every
other candidate, because `src_line` takes the FIRST match) containing verbatim code that
would flip or alter four rows if any of them read this file:

```tcl

```

Poisoned run: **`RESULT: ALL PASS (20 checks)`, rc 0**, and a diff of all 20 detail lines

verified identical (`8338957824ce8f399e63e05077150531`), and run 4 re-confirmed green on

**4. And the output cannot forge a verdict.** A detail string is not only read by humans;
