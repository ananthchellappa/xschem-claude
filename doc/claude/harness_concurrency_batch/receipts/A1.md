## Corrections to PLAN.md — read this before starting B1

**1. NEITHER FIX SHAPE IN "The shape being built" CLOSES THE DEFECT. This is the big one.**
PLAN says `$workroot` "gets the pid scope … Nobody reads scratch after a run, so this is pure
win." Measured, three configurations of the same miniature pair:

| workroot expression | run A | run B |
|---|---|---|
| `"$testname/results/.work"` (today) | 660 phantoms | **died at startup** |
| `"$testname/results/.work.[pid]"` (**PLAN's stated minimum**) | 658 phantoms | **died at startup** |
| `"$testname/.work.[pid]"` (workroot out of `results/`) | 0 phantoms | **died at startup, 2 of 3** |

Pid-scoping `.work` *inside* `results/` is a **no-op for all four faces**: the shared object is
`$testname/results` itself, which every run wipes at startup. Moving the workroot *out* of
`results/` fixes face 1 and is **flaky** on face 2 — and it is the configuration that first
reproduced **face 3** (11 × `awk: cannot open file`, `pathlist=1500 present=844`, run A still
reporting `fatals=0` over 656 files that were gone). **A fix measured once on that shape looks
green.** B1's scope must reach the `results/` root and/or the startup wipe, not only the three
`set workroot` lines.

**2. Face 1's mechanism is mis-attributed.** PLAN says "run A deletes it at its
`:108`/`:100`/`:131` while run B is still reading". Measured: the dominant deleter is the
**startup** wipe (`open_close.tcl:32`), not the end-of-run `file delete -force $workroot`. In
*every* miniature pair run B died at startup and therefore **never reached `:108`** — yet run A
still lost 639–670 status files, all to run B's partially-completed startup wipe. The startup
wipe is both face 2's victim and face 1's principal cause; PLAN describes only the second half.

**3. Face 3 is bigger than "never counted", and needs no concurrency to show.** gawk's "cannot
open file" is a **fatal**, so one missing file aborts the entire `xargs -n 64` batch and files
that *were* present are left un-normalised too — `cleanup_debug_file.awk` only writes a file
back from `endfile()`, and `END{endfile()}` is the only thing that flushes the last file of a
batch. Reproducible race-free in two awk spawns (row `C1b`).

**4. Face 4 is an ERASURE, not a corruption — and the obvious rows ship GREEN.** My first draft
asserted "no NUL bytes" and "not a mixture of two runs". Measured 3/3: the file is **13268
bytes with zero NUL bytes**, run A's verdict **complete and well-formed**, run B's verdict
**entirely absent**, and run B **exits 0** printing `Finish xschemtest.tcl`. Nothing is damaged;
a whole run's answer simply never existed. C1's acceptance must be *"the second run's outcome is
not silently discarded"* — row `V2a` passes if B's block is in the verdict **or** B announced
that it did not take the file, which greens under either branch of R1 (wait, or refuse loudly).

**5. B1's file list is missing one entry.** Row `C1b` targets `test_utility.tcl:102-114`
(`cleanup_debug_files`), which PLAN's B1 row does not list. Without it C1b stays red.

**6. PLAN's line numbers are all correct** — checked individually, no drift. Nothing to fix there.
