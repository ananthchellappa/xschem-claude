## The design choice, and the two things that decided it

**Nothing outside `rotflip` reads the fixture.** Swept repo-wide: the only hits for
`_label_ride_rf` in the entire tree were the `set ::rfsch` line and the issue file itself. So
**there is no canonical name to publish back to** — B1's publish-back pattern is correctly *not*
applied here, and a plain per-run path is the whole answer rather than a lazier one.

**B1's measured trap was checked, not assumed.** Pid-scoping a leaf inside a directory something
else wipes wholesale is a no-op. Nothing wipes `tests/headless/` or `tests/headless/.scratch/`: the
only deleters are `full_audit.sh`'s scratch arm (`:522`, which removes only paths that *appeared
during that run* — "only ever remove paths this run created, never a glob") and `__scratch_sweep`
(dead pid, ≥300 s old). The pid genuinely isolates here, unlike B1's case.

**Why `test_scratch` and not the issue's first suggestion (`_label_ride_rf.[pid].sch` in
`tests/headless/`)** — both measured, not argued:

* That path is **not gitignored**. `.gitignore:84`'s `_*_[0-9]*/` is **directory-only**; verified
  with `git check-ignore -v` on all three candidate spellings, all three `NOT IGNORED`. A corpse
  from a killed run would sit in the developer's `git status` indefinitely.
* The near-miss spelling `_label_ride_rf_[pid].sch` (underscore, not dot) **does** match
  `full_audit.sh:381`'s scratch glob, which is enumerated with `ls -1d` and therefore matches
  **files** as well as directories. Under the default `AUDIT_STRICT_SCRATCH=1` a leaked fixture
  would have become a **fatal audit failure** under a rule written about directories.
* `test_scratch` sidesteps both: `tests/headless/.scratch/` is gitignored (`.gitignore:85`), the
  directory is removed by scratch.tcl's wrapped `exit` on **every** path including the suite's
  failing `exit 1`, and dead-pid corpses are swept on next use. It is also the enforced house
  convention — `full_audit.sh`'s own remediation text says "convert the owning test to
  tests/headless/scratch.tcl" (issue **0148**).

Side effect, deliberate and worth having: the suite now carries the `XSCHEM_SUITE_WATCHDOG_MS`
watchdog it previously lacked. Verified scratch.tcl prints nothing at source time, defines no name
this suite uses, and that the wrapped `exit` preserves both `exit 0` and `exit 1`.

## ⚠ Finding 3 — the row written to detect the defect RE-CREATED it, and I have the measurement

The most valuable thing in this receipt. **W3's first draft planted a sentinel file at the legacy
shared path**, ran `rotflip`, and asserted the sentinel survived. It was green sequentially. Under
ten concurrent pairs it failed **4 of 20**:

```
FAIL: W3 a fixture at the legacy shared path is untouched -> {DELETED} (exp {untouched}) : FAIL
```

— in all four, and nothing else failed. The sentinel was **itself a fixed path in a shared
directory**: two concurrent W3s deleted each other's sentinel. The row written to detect a
fixed-path collision had faithfully reproduced it one layer up, and it would have shipped as a
permanent 20 % flake in a **CI-gated** suite.

**A row that proves a shared path is untouched must not itself use a shared path.** W3 was rewritten
to *observe* rather than plant: it drives the real `rotflip`, then globs the shared directory and
requires it to hold no `_label_ride_rf*` at all. Nothing writes, so concurrent runs cannot disturb
each other; it still reds pre-fix because pre-fix `rotflip` creates exactly that file. Deliberately
absolute ("nothing is there") rather than a before/after delta — a corpse from an older build is
precisely what 0408 complains poisons the next run, so it should be reported rather than subtracted
out. The reasoning and the 4-of-20 measurement are recorded in the file above the row.

**This was only diagnosable in one grep because the detail string reported what was observed**
(`DELETED`). A row printing a canned "the legacy path was disturbed" would have hidden the cause.
