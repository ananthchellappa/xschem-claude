## ⚠ A crude check answered the wrong question again — and this time it was MINE

The batch's running count is four (V1's 75-vs-69, the driver's 16-vs-20, the 7.4-vs-8.5 s
suite cost, D2's escaped-vs-unescaped `set log_fn`). **This is the fifth, and the first a
crew committed against itself.**

I ran `git check-ignore -v tests/create_save/results.999999` as a *non-existent* path and
got **NOT IGNORED**, which contradicts V1's residue table and looked like a V1 error worth
reporting. It is not. `.gitignore:112-117` are **trailing-slash, directory-only**
patterns, and git cannot know an absent path is a directory, so it evaluates it as a file
and correctly reports no match. Settled in a throwaway repo rather than by argument:

```
(a) absent path              -> NOT IGNORED
(b) real directory + file    -> .gitignore:1:tests/create_save/results.*/   (ignored)
(c) git status               -> CLEAN: the directory is invisible to git
(d) find                     -> sees it
```

**V1's table was right; my probe was wrong.** Had I written it up as a V1 error, the next
crew would have inherited a fabricated correction. The lesson generalises past git: *a
check run against a path that does not exist is not a check.* It is also why the decoy
above is a **directory** — a file-shaped decoy would not have matched the pattern under
test and would have proved nothing.

One genuine, small citation slip in V1: it cites `.gitignore:112-114` for **both**
`results.<pid>/` and `.work.<pid>`. `112-114` is `results.*/`; `.work.*/` is **`115-117`**.
