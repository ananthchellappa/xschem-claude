## Group C — ONE decision, three ids: what a broken shipped Tcl helper does
`0658` + `0663` + `0663b`.

**The question:** when one of xschem's own fifteen shipped Tcl helpers fails to
source, should xschem **name the file and exit 1** (what shipped, and what was
chosen *against* the driver's recommendation), or **continue degraded**?

**Lead recommends: keep ABORT.** The measured reason is strong and is in 0663:
every variable `Tcl_AppInit()` reads is set *after* the bare-source block, so
"continue" means `cadlayers=0`, `line_width=0`, `undo_type` NULL, no colours, no
menus, no bindings, no undo — **and that session can still be told to SAVE a
schematic.** Issue 0619 is already open on a session in exactly that state. The
prior behaviour was SIGSEGV (exit 139), so abort-with-a-name is strictly better
than both alternatives.

Note the scope limit, which is the part worth confirming: a broken **PDK** helper
sourced from an `xschemrc` is unaffected — it still survives and exits 0. Only
xschem's *own* shipped helpers abort.

## Group E — the two raw-file trades

### E1 · `0299` — **narrowed last night; the question is smaller than it was**
Should a **binary** raw killed mid-write refuse, or plot a fabricated final point?
Both horns assumed one answer for every raw. The cost is asymmetric in the point
count, and the split resolves it:

* **1-point op/dc** raw, short final point → nothing salvageable; the only point
  *is* the fabricated one. **Refuse.**
* **multi-point** raw, short in its **last** point → every earlier point is
  intact. **Keep the points actually read** (0299's own rejected alternative), so
  a real 59-point transient missing 3 bytes loses **one** point, not all 59.

**Lead recommends the split.** Tonight's crew was told to measure it, not assume
it, and to restate the debt narrowed rather than clear it. **If the crew reports
the split does not hold, this returns to you as originally posed.**

### E2 · `0812` — the shipped security fix's one user-visible trade
The resolver now treats a raw path as **data**. It **drops Tcl array-element
syntax**, so `$a(1)` becomes *value-of-`a`* followed by a literal `(1)`. Nothing
shipped uses that. **But `$env(HOME)/x.raw` goes with it, and that DID resolve at
HEAD.** Nothing in the shipped corpus uses `$env()` either — a user's own
schematic might.

**Lead recommends: accept the drop, then restore `$env(NAME)` as a named special
case.** It is the one spelling with real-world use, it is a closed form the C
scanner can match exactly (`$env(` … `)` with no nesting), and handling it by name
does **not** reopen general array syntax — which is what made the sanitizer
statable in one sentence. That is a small, bounded follow-up, not a re-litigation.
